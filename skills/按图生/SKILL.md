# 按图生 — 双 tab 并行 + 主流程宏观挑 winner（含预审短路）+ 评审闭环

基于参考图风格生成新主题的图片。底层使用**豆包图像生成**，通过 Playwright CDP 自动化。

> **当前版本以 git tag 为唯一版本源**，文档内不维护独立版本号；正文中的「V5.x 新增/改」为历史标注，指向 `CHANGELOG.md` 对应条目。版本演化史与各机制的翻车案例复盘见 `CHANGELOG.md`（执行时不需要读）。

**核心机制**：
- **双 tab 并行**：每轮（首轮 + 所有迭代轮）在 2 个独立 chrome tab 同时跑 A/B 两档 prompt
- **主流程自主挑 winner**：双图生成完，同回合并行 Read 3 张图（原始参考图 + A + B）宏观综合评判，强制输出「两张观察 + 预审判定 + winner + 一句话原因」；两张都明显不达标时预审短路直接迭代（Step 3.7.2.5），不弹 picker 浮窗（终稿确认 confirm 浮窗仍保留）
- **外置评审闭环**：winner 送「按图生-评审」skill，结论权威（通过/修订/重生成），未通过自动迭代
- **发散关（Step 4.1.0）**：评审报的是「问题」不是「解」——写迭代 prompt 前先做 DNA 抖落（删载体前穷举它扛的全部风格特征、没载体接的转移到新载体）+ 加法发散（考虑引入拟合风格且服务主题的新元素）
- **收敛性兜底**：连续 3 轮结论相同 + 关键差异高度重复才打扰用户，否则一直自迭代；交付前必弹终稿确认浮窗
- **中文 JSON 全流程**：所有 prompt 相关流程用中文 JSON，强制 `jq -c .` 序列化

**核心能力**：参考图 + 主题词 → 2 张并行生成图 → **主流程 AI 自主挑 winner** → 评审闭环 → 自迭代直到通过。

**两档策略**：

| 档 | tag | prompt | 押注 |
|---|---|---|---|
| **极简档** | A | **纯自然语言一句话**（如"一个杯子"） | 押豆包自己从参考图悟出风格 |
| **标准档** | B | v3.4 完整中文 JSON（9 字段 + 装饰元素决策） | 押 schema 全覆盖 |

**永远双 tab**：首轮、修订迭代、重生成迭代——**每一轮都跑 A + B 两档**。

## 入口分流

### 方式 1：用户直接调用（从 Step 1 开始）
用户提供**参考图** + **新主题**，从 Step 1 正常执行完整流程。

### 方式 2：v7.0.0 后已无「评审推送回跳」——评审在独立进程里，写文件交接
v7.0.0 起评审改为独立 `claude -p` 进程（见 Step 4「触发评审」），**评审进程不再向主流程推送继续指令、不再走循环卡回跳**——它只把结论 Write 到 `<temp_dir>/review-result-第N轮.json`。主流程在 Step 4 fire 评审脚本后**自己轮询读该文件**拿结论，然后：

- 结论 `通过` → 主流程自己进入 **Step 5 交付**
- 结论 `修订` → 主流程自己进入 **Step 4.1 修订**（双档迭代）
- 结论 `重生成` → 主流程自己进入 **Step 4.1 重生成**（双档迭代）

轮次 / 参考图路径 / 主题 / 交付落点 等字段主流程本地已持有（`pick_payload` + Step 1 入参），无需评审进程回传；评审结论 JSON 里的 `结论详情` / `关键差异前三` / `风格味道评判` / `门类证据` 供 Step 4.1 写迭代 prompt 时消费。

**判断依据**：主流程始终从 Step 1 开始；评审是主流程内 Step 4 fire 出去的独立进程，不构成本 skill 的「入口」。（历史：v6.x 及之前评审在同上下文跑、经循环卡/Skill 回跳，v7.0.0 因同上下文放水问题废弃该机制，见 CHANGELOG。）

## Step 1: 接收任务

用户提供**参考图** + **新主题**，明确要求"按这个风格生成 X"。

**可选入参 `交付落点`（v6.7.0）**：调用方（如 liaison 复刻主流程）可传一个**绝对路径或项目相对路径**作为终稿落点，让资产直接归置到调用方指定的位置。
- **传了** → Step 5.1 把终稿 `cp` 到该路径（含文件名），不落桌面。
- **没传**（人工直接调用是常态）→ Step 5.1 回退默认 `~/Desktop/<theme>-终稿.png`。
- 该字段全程随任务透传：交给评审 skill 时放进入参，评审 `推送载荷` 原样带回，Step 5 消费。评审主体**不读取**它（与 `轮次` 同为纯透传字段）。

## Step 1.5: 填参考图分类卡（强制中文 JSON 输出，先于写 prompt）

**前置必读**（仅本次任务第一次进入时需要）：
```
Read ~/.claude/skills/按图生/STYLE-CARD.md
```

**填卡纪律**：
1. 严格按 STYLE-CARD.md 的「机械识别锚点」逐字段对照填写
2. **输出必须是合法中文 JSON**，符合 STYLE-CARD.md 规定的 schema（字段名 + 枚举值全中文）
3. **9 个 风格 字段全填**（维度 / 渲染 / 光影 / 媒介 / 填充模式 / 边缘 / 构图 / 背景 / 配色）+ `装饰元素` 装饰元素清单数组。写不出值就填 `"未知"` 并在 `备注` 字段说明
4. **本卡是 Step 2 写 prompt B（标准档）的唯一事实来源**——B 档 prompt 用词必须与卡一致
5. **装饰元素 必须列全**——所有非主体的装饰/辅助元素都要列；漏列会导致 Step 2.3 装饰元素迁移决策跑空
6. **填充模式.值 === "线性描边" 时 描边连续性 必填**

**输出格式（强制中文 JSON）**：参见 STYLE-CARD.md schema。

**自检**（填完卡后回头看一眼参考图，任一答 No 就回去补）：
1. JSON 是否合法？字段名是否全中文？
2. "如果我只看这张卡、不看图，能否复述出参考图的核心风貌？"
3. "装饰元素 是否覆盖了参考图里所有非主体装饰物？还有没有漏掉的小元素（背景纹理/角标/分隔线/底部条/磨砂层/小图标）？"

## Step 2: 写两份 Prompt JSON（A 极简 + B 标准）

**前置必读**（本次任务第一次进入 Step 2 时需要）：
```
Read ~/.claude/skills/按图生/PROMPT-RULES.md
```

PROMPT-RULES.md（V4.1 中文 JSON 版）包含：
- **2.0 Prompt JSON Schema**：完整字段定义和数据类型（字段名 + 枚举值全中文）
- **2.1 起手式判断**：极简 vs 详细
- **2.2 必须遵守的铁律 1-6**：主体.类型 元属性词 / 输出 字段 / 卡-prompt 一致性自检
- **2.3 装饰元素迁移决策**（V2.8 强制）：每个 `主题相关: true` 的元素必须做 `决策: "保留" | "替换" | "移除"` 三选一
  - **2.3.0 首轮决策前置闸门（V5.3.3 强制）**：做任何 `移除` / `替换` 前，必须先把 Step 4.1.0 的「DNA 抖落 + 加法发散」在首轮跑一遍——删/改元素前开放穷举它扛的全部 DNA（颜色/锚点位/质感/结构…），没载体接的特征禁止裸删、降级为替换；删"服务旧主题的构图元素"时必问一次"该构图语言能否用新主题语义换载体保留"。**目的：首轮就带 DNA 守恒决策，不靠用户 REVISE 事后补救**
- **2.5 自检 checklist**

### 双档要求（V4.0 引入，V5.0 沿用）

**A 档（极简）**——**纯自然语言一句话**，不用 JSON、不读 STYLE-CARD、不写任何风格描述：
- 示例：`一个杯子` / `一支铅笔` / `一只猫` / `搜索图标`
- **不堆砌形容词**，不带风格词、不带颜色、不带材质
- 押注：参考图被一同上传给豆包，豆包自己从参考图悟出风格
- 极短为佳——通常 2-6 个中文字符就够；最长不超过一句话（不超过 15 个汉字）
- **禁止**写成"按这个风格做一个杯子"——这种自我提示词反而会让豆包过度推断
- **前缀由脚本自动补，主流程不要自己写**：`doubao-gen.mjs` 会把 `--prompt-a` 的值统一拼成 `帮我按照参考图，生成<你写的主体>` 再发给豆包（如传 `一支铅笔` → 实际发送 `帮我按照参考图，生成一支铅笔`）。所以 `PROMPT_A` 只写**主体大白话**即可，写了前缀也不会重复拼接，但**别手写**——保持首轮/迭代轮口径一致

**B 档（标准）**——沿用 v3.4 完整规则（中文 JSON）：
- 走 PROMPT-RULES.md 全流程
- 必须包含 9 字段 `风格` + `装饰元素决策` + `排除` + `输出`
- 字段必须与 Step 1.5 的 STYLE-CARD JSON 卡一致

两份 prompt 都是合法中文 JSON，存到两个临时文件。

## Step 3: 执行双 tab 并行生成

### 命令格式（双 tab 模式，必须带 `--auto-review`）

```bash
# 1. A 档：纯自然语言一句话（直接字符串，不用 JSON、不用 jq）
PROMPT_A="一支铅笔"

# 2. B 档：写完整中文 JSON 到临时文件 → jq -c . 序列化
cat > /tmp/prompt-b-standard.json <<'EOF'
{
  "主体": {"主体描述": "铅笔", "类型": "图标", "动作": null, "服装": null},
  "风格": {...},
  "装饰元素决策": [...],
  "排除": [...],
  "输出": "单张图片"
}
EOF
PROMPT_B=$(jq -c . /tmp/prompt-b-standard.json)

# 3. 调用豆包双 tab 并行生成
node ~/.claude/skills/按图生/doubao-gen.mjs \
  --ref <参考图路径> \
  --prompt-a "$PROMPT_A" \
  --prompt-b "$PROMPT_B" \
  --theme "<用户给定的主题词>" \
  --round 1 \
  --auto-review
```

**B 档为什么必须用 `jq -c .` 而不是 `python json.dumps`**：
- `jq -c .` 默认保留 UTF-8 → 输出 `"主体描述":"铅笔"`
- `python3 -c "json.dumps(...)"` 默认 `ensure_ascii=True` → 中文被 escape 成 `\uXXXX`，豆包读不懂

**A 档直接用 shell 字符串**，无序列化问题，无需 jq。

脚本自动完成：连接 CDP → **开 2 个新 tab** → 并行（A、B 同时）粘贴参考图 → 各自填自己的 prompt → 各自提交 → 各自等待生成 → 各自下载 2048 原图到：
- `/tmp/按图生-评审/{任务ID}/第N轮-候选A-极简.png`
- `/tmp/按图生-评审/{任务ID}/第N轮-候选B-标准.png`

最后输出 handoff JSON + `MAIN_PICK_WINNER` 指令。

**重要**：
- `--auto-review --theme` 是评审自动化闭环的入口
- 第一轮默认 `--round 1`，迭代递增 `--round 2`、`--round 3`...
- 双档共用同一参考图（`--ref` 只有一个）

### Step 3.5: 解析脚本输出（机器→主进程握手）

脚本最后一行 JSON 形如：

```json
{
  "status": "generated",
  "mode": "dual",
  "candidates": [
    {"tag":"A","complexity":"极简","path":"/tmp/.../第1轮-候选A-极简.png"},
    {"tag":"B","complexity":"标准","path":"/tmp/.../第1轮-候选B-标准.png"}
  ],
  "errors": [],
  "temp_dir": "/tmp/按图生-评审/...",
  "task_id": "...",
  "round": 1,
  "next_action": "main_pick_winner",
  "original_ref_path": "/Users/.../原始参考图.png",
  "pick_payload": {
    "ref_path": "/Users/.../本轮参考图.png",
    "orig_ref_path": "/Users/.../原始参考图.png",
    "candidates": [
      {"tag": "A", "complexity": "极简", "path": "/tmp/.../第1轮-候选A-极简.png"},
      {"tag": "B", "complexity": "标准", "path": "/tmp/.../第1轮-候选B-标准.png"}
    ],
    "theme": "...",
    "round": 1,
    "temp_dir": "/tmp/按图生-评审/...",
    "note": "V5.0 主流程自主挑 winner：同回合内并行 Read 3 张图..."
  }
}
MAIN_PICK_WINNER
```

**根据 `next_action` 路由**：

| `next_action` | 含义 | 主流程动作 |
|---|---|---|
| `main_pick_winner` | V5.0 唯一主路径（双图或单图都走这条） | 进入 **Step 3.7（主流程宏观挑 winner）** |
| `await_user` | 没带 `--auto-review`，按用户要求处理 | — |

**V5.0 变更**：脚本不再唤起 picker 浮窗，handoff 总是返回 `main_pick_winner`。主流程自主完成挑 winner 动作（同回合并行 Read 3 张图 + 宏观综合评判）。

**禁止**输出"生成完成请告诉我是否要评审/挑图"之类等待提示，**禁止**自行评审，**禁止**自行打分。**唯一允许的下一动作**：进入 Step 3.7。

## Step 3.7: 主流程宏观挑 winner（V5.0 全自动主路径）

V5.0 不再有用户 picker 浮窗，主流程接管挑 winner。

### 单图情况（candidates 只有 1 张）

直接把这张当 winner：

```bash
mv <唯一候选路径> <temp_dir>/第N轮-winner.png
```

然后进入 Step 4 评审。

### 双图情况（candidates = A + B，主流程核心）

#### Step 3.7.1: 同回合内并行 Read 3 张图（强制）

```
Read(pick_payload.orig_ref_path)
Read(pick_payload.candidates[0].path)   # A 极简
Read(pick_payload.candidates[1].path)   # B 标准
```

**铁律**：必须在同一回合内并行发出 3 个 Read，禁止跳过、禁止 sequential。

#### Step 3.7.2: 宏观综合评判（强制按下面这个 prompt 自我对话）

读完 3 张图，主流程必须按下面这个**结构化文本**输出（不需要 JSON），评判维度是**宏观综合**——不局限在形态：

```
【候选 A 一句话观察】<对 A 的客观描述，覆盖风格贴合度 + 主体形态造型力 + 主题贴合度 + 整体观感，30-80 字>
【候选 B 一句话观察】<同上，对 B>
【预审判定】两张达标 / 至少一张达标 / 两张都明显不达标
【Winner】A 或 B 或 无（两张都明显不达标时填「无」，走 Step 3.7.2.5 短路直接迭代）
【一句话原因】<选这张的具体差异点 / 或两张都不达标的共同硬伤，不能写"A 更好"这种空话>
```

**铁律**：

1. **必须先输出 A、B 两段观察，再输出预审判定 + winner + 原因**——禁止跳过观察直接给结论
2. **评判维度是宏观综合**（风格 + 形态 + 主题 + 整体观感），**不要只看形态、不要只看风格**——任一单维度都不足以判好坏
3. **一句话原因必须落到具体差异点**：
   - ❌ "A 整体更好" / "B 更符合参考图" / "A 更精致"（虚）
   - ✅ "A 的颈肩过渡比 B 自然，B 的肩部是直角梯形显得生硬" / "A 配色更接近参考图的低饱和哑光，B 偏鲜艳"（实）
4. **预审短路（V5.7 新增）**：若**两张都明显不达标**（都有阻塞级硬伤：如都严重脱离主题 / 都丢主导色 DNA / 都没满足用户本轮明确诉求 / 都形态崩坏），`预审判定` 填「两张都明显不达标」、`Winner` 填「无」→ **不强制选 winner、不送评审**，直接走 **Step 3.7.2.5** 进入 Step 4.1 迭代优化。只要**至少一张达标或接近达标**（哪怕另一张差），就正常选 winner 送评审。**判「都不达标」的门槛要严**——必须是 A、B 都有**同一类阻塞级硬伤**、选谁送评审都是白跑一轮评审，才短路；只是「都有小瑕疵但方向对」不算，仍选较好的一张送评审
5. **不要参照"应该长什么样"的预设**——只看眼前 3 张图，用主题词（pick_payload.theme）作为评判锚点；预审判定的达标锚点 = 主题贴合 + 参考图风格 DNA + 本轮用户诉求（若有）

#### Step 3.7.2.5: 预审短路——两张都不达标直接迭代（V5.7 新增）

**仅当 Step 3.7.2 的 `预审判定 === "两张都明显不达标"`（`Winner === 无`）时走本步**；否则跳过，直接进 Step 3.7.3。

**动作**：不选 winner、不送评审，把两张候选都留档，**主流程自己充当"评审结论"直接触发 Step 4.1 迭代**——因为两张都有阻塞级硬伤、送评审必然也是「修订/重生成」，跳过评审省一轮。

1. **归档两张候选**（不 rm、不 mv 成 winner，改名留证便于回溯）：
   ```bash
   TEMP_DIR=<pick_payload.temp_dir>
   ROUND=<pick_payload.round>
   mv "$TEMP_DIR/第${ROUND}轮-候选A-极简.png" "$TEMP_DIR/第${ROUND}轮-预审淘汰A.png"
   mv "$TEMP_DIR/第${ROUND}轮-候选B-标准.png" "$TEMP_DIR/第${ROUND}轮-预审淘汰B.png"
   ```
2. **写 iteration-log**（结论记为「预审短路-迭代」+ 两张的共同硬伤，供收敛性兜底检测，逻辑同 Step 4 的 log 累积）。
3. **自定迭代类型**：由 Step 3.7.2 观察出的共同硬伤性质决定——
   - 共同硬伤是**风格门类/主题完全偏**（如都画错主题、都丢主导色 DNA、都门类跨界）→ 走 **Step 4.1 重生成**（策略 A）
   - 共同硬伤是**方向对但都没执行到位**（如都没满足用户本轮明确诉求、都残留该删的元素、都小幅偏色）→ 走 **Step 4.1 修订**（策略 B），把「两张的共同硬伤 + 用户本轮诉求（若有）」当作最高优先信号喂 A/B 档
4. **`--ref` 选择**：修订用**两张里较接近目标的那张**当参考图（喂豆包一个"底子对但要改 X"的起点）；重生成用**原始参考图**。`--orig-ref` 始终是首轮原始参考图。
5. 直接进入 **Step 4.1 双档迭代**，跑完再回 Step 3.5 → 3.7 闭环。

**铁律**：
- 预审短路**不经过评审 skill**——主流程直接下「迭代」结论。这是唯一允许主流程绕过评审的场景，且**仅在两张都明显不达标时**成立（Step 3.7.2 严门槛把关）
- 短路后**仍写 iteration-log + 仍做收敛性兜底**——防止「两张都不达标」反复发作时陷入死循环不打扰用户的漏洞
- **短路≠降低质量门槛**——它只是省掉"选一张明知不达标的图去走评审、评审必然打回"这一空转，最终交付仍要走完整评审 + Step 5.0 用户确认

#### Step 3.7.3: 执行挑选结果（机械动作）

**仅当 `预审判定 !== "两张都明显不达标"`（选出了 winner）时走本步。**

```bash
WINNER_TAG=<A 或 B>
LOSER_TAG=<另一个>
WINNER_PATH=<对应 pick_payload.candidates 里那个 tag 的 path>
LOSER_PATH=<另一个 pick_payload.candidates 元素>
TEMP_DIR=<pick_payload.temp_dir>
ROUND=<pick_payload.round>

rm "$LOSER_PATH"
mv "$WINNER_PATH" "$TEMP_DIR/第${ROUND}轮-winner.png"
```

#### Step 3.7.4: 进入 Step 4 评审

把 `第N轮-winner.png` 路径作为评审的 `image_paths[0]` 送入按图生-评审 skill。

### V5.0 核心铁律

- **3 张图必须 Read，禁止凭空判**——回合内并行 3 个 Read，少一个都算违规
- **输出顺序必须是「两段观察 → 预审判定 → winner → 原因」**——倒序或跳步都算违规
- **评判维度是宏观综合**——不局限形态、不局限风格、不局限主题，全部一起看
- **挑 winner 的 picker 浮窗（三图对比）已废弃**——winner 由主流程自主 Read 三图判定，不再弹窗让用户挑。（注意：这与 **Step 5.0 的终稿确认 confirm 浮窗**是两回事——后者在交付前必弹，仍在用）
- **预审短路分支（V5.7）**：两张都明显不达标（同类阻塞级硬伤，选谁送评审都白跑一轮）→ 走 Step 3.7.2.5 直接迭代、不选 winner、不送评审。**门槛要严**——只要至少一张达标/接近达标就正常选 winner 送评审，不滥用短路。短路仍写 iteration-log + 走收敛性兜底，不降低最终质量门槛

## Step 4: 验收（外置评审 skill）

### 触发评审（v7.0.0 改：独立进程评审，杜绝同上下文放水）

> **v7.0.0 核心变更（防放水）**：评审**不再在主生图 CC 上下文里跑**（无论 Skill 调用还是循环卡直评）。同一上下文里评审自己刚生成的图会天然放水——主流程有"想让自己的图过"的隐性动机，fresh-eyes 是伪的。改为 fire 一个**独立 `claude -p` 进程**（= 独立上下文 = 真 fresh-eyes，实测同两张图主进程判"通过"、独立进程判"修订"），由 `review-headless.sh` 封装：独立进程自己 Read 评审 skill 全套文档、真 Read 两张图看像素、走完整评审流程、把中文 JSON 结论 Write 到 `<temp_dir>/review-result-第N轮.json`，主流程轮询读取该文件拿结论。**原「循环卡回跳 / Skill 同上下文调用」两条路径均废弃**（独立进程不需要回跳，写文件即交接）。

**触发命令（每一轮送审都走这条，无首轮/后续之分）**：

```bash
REVIEW_JSON=$(bash ~/.claude/skills/按图生-评审/review-headless.sh \
  --ref "<pick_payload.orig_ref_path>" \
  --image "<temp_dir>/第N轮-winner.png" \
  --theme "<pick_payload.theme>" \
  --temp-dir "<temp_dir>" \
  --round "<pick_payload.round>")
# 脚本内部已阻塞等独立评审进程结束、校验产物、最后一行输出握手 JSON：
#   {"status":"ok","result_path":"<temp_dir>/review-result-第N轮.json","round":N,"child_exit":0}
# 取握手 JSON 里的 result_path，Read 它拿到完整中文 JSON 评审结论。
RESULT_PATH=$(echo "$REVIEW_JSON" | tail -1 | jq -r '.result_path')
```

**拿结论**：脚本返回 `status:ok` 后，**Read `$RESULT_PATH`**（即 `<temp_dir>/review-result-第N轮.json`）拿到评审 skill 规定的完整中文 JSON 结论，按下方「处理评审返回」路由。

**入参对齐（脚本参数 ↔ 评审 skill 契约）**：
- `--ref` = **`pick_payload.orig_ref_path`（首轮用户给的最原始参考图，评审锚点，永不漂移）** ⚠️ **禁止**传 `ref_path`（迭代轮的上轮 winner）——那会让评审锚点逐轮漂移、偏离累积（第2轮拿第1轮当参考，但第1轮自己可能已偏离原始参考图）。评审的使命是"生成图 vs 用户最初参考图 是否同风格"，锚点必须钉在原始参考图。
- `--image` = `<temp_dir>/第N轮-winner.png`（Step 3.7.3 rm 落选 + mv winner 后的路径）
- `--theme` = `pick_payload.theme`
- `--temp-dir` = `pick_payload.temp_dir`（结果 JSON 落此目录，跨轮共享）
- `--round` = `pick_payload.round`（**仅用于结果文件命名**，脚本不把轮次喂给评审主体——评审 skill 的 fresh-eyes 铁律照旧守住）

**禁止传入 prompt 字段**——脚本本就不接 prompt 参数，评审必须基于纯视觉观察。

**为什么独立进程天然更严**：独立 `claude -p` 进程与主流程零共享上下文——它不知道图是谁生成的、第几轮、上轮评审说过什么，冷启动看两张图，没有"图是我生的、让它过"的动机。这正是同上下文评审做不到的真 fresh-eyes。

**user_complaint 字段（v7.0.0 调整）**：自动闭环链路默认不传（评审要 fresh-eyes），当前 `review-headless.sh` 不接该参数。用户主观吐槽走 **Step 5.0 终稿确认浮窗 → Step 4.1 修订** 那条路（见 Step 5），不进评审进程。

**异常兜底**：脚本返回 `status:error`（`child_nonzero_exit` / `result_file_missing_or_empty` / `result_not_valid_json`）或退出码非 0 → 独立评审进程异常，**报错给用户、不静默当通过**、不重试（同「双 tab 全失败」纪律）。

### 处理评审返回并自动执行

| 结论 | 自动执行动作 |
|---|---|
| `通过` | 立即进入 **Step 5（交付）** |
| `修订` | 立即进入 **Step 4.1 双档迭代（修订）** |
| `重生成` | 立即进入 **Step 4.1 双档迭代（重生成）** |

**铁律**：
- **不得**绕过 `按图生-评审` 自己判定通过
- **不得**软化 `重生成` / `修订` 结论
- **不得**收到结论后停下问用户"要不要执行"
- **不得**在执行策略前重新分析"是否真需要迭代"——评审 skill 是权威

**唯一例外**（需要用户介入）：
- **收敛性兜底**：每轮评审结束后，主流程把 `(round, 结论, 关键差异前三)` 追加到 `<temp_dir>/iteration-log.json`。
  当文件里**连续 3 轮**满足以下条件时 → 停下来向用户汇报「陷入相同问题循环」，建议手动介入：
    a. 评审结论完全相同（都是「重生成」或都是「修订」）
    b. 且每轮的「关键差异前三」之间相似度 ≥ 80%（3 条差异里至少 2 条语义相同/高度重叠）
  否则**一直自迭代不打扰用户**——不限轮数，不每 N 轮汇报。
- 用户显式去掉 `--auto-review` → 走人工评审路径

**收敛性检测实现**（伪代码，在每次评审结束、进入 Step 4.1 之前执行）：

```javascript
// 每轮评审完后追加
const logPath = `${temp_dir}/iteration-log.json`;
const raw = fs.existsSync(logPath) ? fs.readFileSync(logPath, "utf8") : "[]";
const log = JSON.parse(raw);
log.push({ round, 结论, 关键差异前三 });
fs.writeFileSync(logPath, JSON.stringify(log, null, 2));

// 第 4 轮起做检测
if (log.length >= 3) {
  const last3 = log.slice(-3);
  const sameConclusion = last3.every(x => x.结论 === last3[0].结论) && last3[0].结论 !== "通过";
  if (sameConclusion) {
    // 判定关键差异前三相似度：每两轮之间，3 条差异里至少有 2 条语义重叠 = 高度相似
    const r1 = similar(last3[0].关键差异前三, last3[1].关键差异前三);
    const r2 = similar(last3[1].关键差异前三, last3[2].关键差异前三);
    if (r1 && r2) {
      // 死循环汇报：停下来告诉用户
      报告({
        消息: "连续 3 轮陷入相同问题循环",
        最近3轮: last3,
        建议: "手动介入：换参考图 / 换主题描述 / 手动调 prompt"
      });
      return;  // 不再自迭代
    }
  }
}
// 否则继续自迭代
```

主流程不需要写代码做相似度判断——可以由 LLM 直接读 last3 数据后用语义判断。重点是**强制每轮追加 log 文件 + 每轮做检测**这两个动作。

**iteration-log.json 生命周期**：

- `temp_dir` 由首轮 doubao-gen.mjs 创建（基于 task_id），**所有迭代轮次共享同一个 temp_dir**——脚本不为每轮新建目录
- iteration-log.json 在该 temp_dir 内**跨轮累积**——首轮评审完后写入第 1 条；第 2 轮追加第 2 条；……
- 迭代触发新一轮 doubao-gen 时，**必须**继续把 `--ref` / `--orig-ref` 落到同一个 temp_dir 下（脚本通过 task_id 路由）；不要改写 temp_dir 路径
- 主流程在每轮评审结束后，**先读 iteration-log.json**（不存在则视为空数组——首轮场景），追加本轮记录，再写回；然后判定收敛性

## Step 4.1: 双档迭代（永远双 tab）

无论是修订还是重生成，**始终跑 A + B 两档**。两档独立生成 → 主流程 Step 3.7 宏观挑 winner → 重新评审。

### Step 4.1.0: 发散——评审报的是「问题」，不是「解」（写 prompt 前必做）

**铁律：评审给的是「问题描述」，不是「唯一解法」。写迭代 prompt 之前，必须先在解空间里发散一步。**（典型反例：评审报「外框冗余」直接翻译成「删框」，但深蓝黑框是主导色载体，删框=丢主导色——正解是「去框 + 深蓝黑转剪影描边」的第三条路。）

**触发条件**：迭代涉及**删除或大改任何一个载体**（形状/板/框/叠层/容器等参考图里的视觉元素）时——一律先做下面的「DNA 抖落」，不要等"感觉有冲突"才做。

**强制动作**：

1. **先把评审结论拆成「问题」而非「动作」**——「外框冗余」是问题（外框作为容器在头像槽里碍事），不是「删掉外框」这个动作。

2. **【核心】DNA 抖落——对着「要删/改的那个载体」，把它身上扛的全部风格特征穷举出来。**

   > 穷举而非清单：封闭清单永远漏下一个维度——对着这个具体要删的载体，把所有可指认的东西全抖出来才不漏。

   **做法**：盯着原始参考图里**这个要删的载体**，逐项写出它承载了哪些风格特征。**至少覆盖但不限于**以下维度（写不出就明确写「无」，但必须逐项过一遍）：
   - **颜色**：它身上有没有 `占比:主导`/`次要` 的色？
   - **材质 / 质感**：玻璃 / 磨砂 / 金属 / 厚度感 / 表面纹理（划痕、磨损、颗粒）？
   - **结构**：叠层 / 错位 / 层次关系 / 它和主体的空间结构？
   - **光学**：通透折射 / 边缘高光带 / 内发光 / 投影？
   - **其它任何你盯着它能看出来的特征**——这一条强制你别停在上面四项，继续抖。

   **逐项追问**：每抖出一个特征，立刻问一句「删掉这个载体后，这个特征**有没有别的载体接住**？」
   - 有别的载体接住 → 安全。
   - **没有别的载体接住 → 这个特征会随载体一起丢失 = 风格 DNA 丢失**，必须在第 3 步给它找新载体（转移），不能放任它消失。（反例复盘见 CHANGELOG「V5.3.1 DNA 抖落」——删玻璃底板只查颜色，丢了厚玻璃折射质感和叠层。）

3. **问：有没有同时满足冲突双方的第三条路？** 把第 2 步抖出的「没载体接的特征」逐一转移/保留，典型发散方向（不穷举，按情况想）：
   - **解耦「特征」与「载体」**：载体形状可删，但把它承载的风格特征（颜色 / 质感 / 结构…）**转移到新载体**上。例：删深蓝外框 → 深蓝黑转主体描边；删玻璃底板 → 厚玻璃质感转主体本身。
   - **缩小/弱化而非删除**：把碍事的元素改小、改细、改成不干扰主体的形态。
   - **替换载体**：同一特征换一个不冲突的呈现。

   **⚠️ 特例：冲突双方是「用户诉求 vs 评审风格锚点」时（V5.8 新增，实战翻车血泪）——最容易陷死循环，第三条路不是可选而是必须。**

   > **病根（实战复盘）**：用户要求**删掉参考图某个结构性载体**（如"去掉这两个方块""不要外框"），而这个载体恰好是**评审拿原图当锚认定的风格骨架本身**（双层错位方块 = app 图标风格 DNA / 外框 = 卡片语言）。此时直接把用户诉求翻成"删载体"动作 → 评审锚点仍钉在含该骨架的原图 → **无论新图画多好，评审必判「同风格=否/重画」，且连删连打回，陷死循环**。这不是画得差，是「用户要删的 = 评审的锚点」这两个标准在对立。汽车案例连续 2 轮（删方块→纯剪影车、删方块→等距色块车）都撞这堵墙，直到把「层叠形式」当骨架保留、只换载体形状才通过。
   >
   > **识别信号**：用户 REVISE 说"去掉/删掉某个结构性载体"，而这个载体在参考图卡里是**扛主导/次要色 + 承载"容器/叠层/错位/描边框"这类构图语言**的大件 → 极可能撞评审锚点。

   **强制解法——把「构图形式」和「载体形状」分开，只换形状、保住形式**：
   - **别删构图语言，只换承载它的具体形状**：用户嫌的往往是"载体的具体形状"（干巴巴的方块），不是"构图关系"（双层错位）。保留**构图形式**（层叠 / 错位 / 容器 / 描边框这套关系 = 评审要的骨架），把**载体形状**换成主题元素（用户要的内容）。汽车案例正解：方块层叠 → 换成"前层蓝紫渐变车 + 后层黑色错位车影"，层叠 DNA 在（评审过）、画面全是车（用户满意）。
   - **在 `迭代.保持` 里显式钉住"要保留的构图形式"**（如"左上错位叠层关系不变""容器/描边框结构不变"），在 `迭代.调整` 里只写"把方块/外框的形状换成 XX 主题元素"——让豆包明白是换载体不是拆骨架。
   - **过不了这一步（构图形式实在无法用主题元素承载）才升级打扰用户**：走 Step 4 收敛性兜底那条路，向用户摊明"你要删的正是评审的风格锚点，二者对立"，让用户在"以我诉求为准关掉评审"和"保留骨架"之间拍板——**但先穷尽第三条路，别一撞墙就甩给用户**。

4. **【加法发散——破除"只减不加"盲区】问一句：这个主题下，有没有一个「既拟合参考图风格、又对主题有真实贡献」的新元素值得加？**（发散不只是在现有元素上动刀——新主题下可以引入符合风格、又服务主题的新元素，如头像玻璃光环、薄荷绿氛围光点。）

   **要加，这个新元素必须同时过三关（缺一就不加）**：
   - **① 拟合风格**：用参考图同一套风格 DNA 呈现（如玻璃质感、薄荷绿辉光），不是异质贴片。
   - **② 对主题有真实贡献**：是主题语义的一部分（头像光环=头像氛围、玻璃描边框=头像槽语义），**不是装饰残留**——能经得起评审「这元素对主题有没有贡献」的拷问。这跟评审删冗余是**同一把尺子、方向相反**：评审删「有风格、无主题贡献」的；加法加「有风格、且有主题贡献」的——所以二者不打架（评审永远不会删一个真有主题贡献的元素）。
   - **③ 克制、不抢主体**：不让画面变满、不喧宾夺主。高级感常来自克制（参考图本身也不花）。

   **默认答案是「不加」**：问的目的是"确保我考虑过加法"，不是"逼我每轮都塞东西"。三关有任一过不了 → 老实不加。**警惕"自我说服"**：别给一个其实没主题贡献的元素硬编"它服务主题"的理由（就像评审曾给外框硬编"它是头像卡"一样）。

5. **把发散出的第三条路（含减法转移 + 可选的加法新元素）写进迭代 prompt**（A 档点出方向、B 档填 `迭代.调整` + `迭代.保持` 显式列出"要转移保住的 DNA 特征" + 如有加法则在 `装饰元素决策` 里以 `决策:"新增"` 写明新元素及其三关理由），而不是把问题直接翻成删除动作。

**边界（严格遵守）**：发散**只在「兼顾本次冲突 + 把当前主题表达得更丰满」的范围内**——**不改主题、不引入与当前主题无关的元素**。加法允许"为把当前主题表达得更丰满而引入服务该主题的新元素"，但不允许"跑去做别的主题 / 加无关装饰"。目标是「同时满足评审的问题 + 保住被删载体的全部风格 DNA + （可选）用拟合风格的新元素丰富主题表达」，不是重新设计。

### 修订（评审给 `修订`）：渐进式微调

**前置必读**（仅本任务第一次进入修订时）：
```
Read ~/.claude/skills/按图生/PROGRESSIVE-ITERATION.md
```

**A 档（极简）—— 用大白话点出评审最严重的 1 个问题方向**：

仍是**纯自然语言一句话**、不用 JSON、不结构化。但**不再机械换措辞**——评审 skill 已经告诉你问题在哪了，A 档要做的是**用一句最短的口语化大白话**，把评审「关键差异前三」里**最严重的 1 条**直接说出来。

**写作纪律**：
- 比首轮 prompt 长度多 1-3 个词为佳（首轮 "一个文件夹" → 修订 "淡粉色的文件夹"）
- 用**正向描述目标状态**，不用"减少/不要"等负面词
- **不写风格词**（"扁平/3D/玻璃/磨砂"这些是 B 档的活）
- 只**挑 1 个问题**说，不堆 2-3 个问题（堆了反而又退化为 B 档形态）

**对照范例**（评审给的问题 → A 档 prompt）：

| 评审最严重问题 | ❌ 死板换措辞 | ✅ 大白话点出方向 |
|---|---|---|
| 配色过艳、对勾凸起、高光太大 | "文件夹图标" | "淡粉色的文件夹" |
| 主体不够像主题（被装饰抢戏） | "一个文件夹" | "标签条文件夹" |
| 主体太大、占满画面 | "一个文件夹" | "小一点的文件夹" |
| 主体太硬 / 太机械 | "一只猫" | "可爱的小猫" |
| 主题被周边元素污染 | "勇气" | "干净的勇气图标" |

**押注**：豆包看参考图悟整体风格 + 拿到一个最关键的"避免再错"信号 → 不需要长篇大论。

**B 档（标准）—— 完整 `迭代` 字段，沿用 v3.4 协议**：
- 带 `迭代` 字段，包含 `保持` / `调整` / `边界`
- 遵循 PROGRESSIVE-ITERATION.md 5 铁律 + 4 教训
- 评审给的 `细节差异` / `语义脱锚元素` 用来填 `调整` 数组

```bash
# A 档：大白话点出评审最严重的 1 个问题方向（不结构化，比首轮多 1-3 个词）
PROMPT_A="淡粉色的文件夹"   # 例：评审说配色过艳是首要问题

# B 档：写迭代 JSON 到临时文件，jq 序列化
cat > /tmp/prompt-b-iter.json <<'EOF'
{
  "迭代": {"模式":"渐进式","保持":"...","调整":[...],"边界":[...]},
  "主体": {...},
  "风格": {...},
  "排除": [...],
  "输出": "单张图片"
}
EOF
PROMPT_B=$(jq -c . /tmp/prompt-b-iter.json)

node ~/.claude/skills/按图生/doubao-gen.mjs \
  --ref <上轮 winner 路径> \
  --orig-ref <首轮原始参考图路径> \
  --prompt-a "$PROMPT_A" \
  --prompt-b "$PROMPT_B" \
  --theme "<theme>" \
  --round <round+1> \
  --auto-review
```

- `--ref`：**两档共用上轮 winner**（与 v3.4 渐进式迭代一致）—— 喂给豆包的"参考图"
- `--orig-ref`：**首轮用户给的那张原始参考图**（不变量）。直接用上一轮 handoff JSON 里的 `original_ref_path` 字段（脚本会一直透传）。透传到 `pick_payload.orig_ref_path`，**双重用途**：① 供 Step 3.7.1 挑 winner 时并行 Read 三图的对照；② **供 Step 4 评审的 `--ref` 锚点**（评审必须拿原始参考图当锚，不能用会漂移的上轮 winner）。**迭代轮必须传 `--orig-ref`**——漏传会导致 `orig_ref_path` 回落成上轮 winner，评审锚点跟着漂移
- `--round`：评审 push 进来的 round + 1

### 重生成（评审给 `重生成`）：完全重写

**A 档（极简）—— 用大白话点出评审「风格偏离方向」的最严重 1 条**：

仍是**纯自然语言一句话**、不用 JSON。但和首轮**不一样**——评审给了"风格偏离方向"清单（如"维度一票否决：二维扁平 vs 三维渲染"），A 档要把**最严重那条偏离方向反过来用大白话讲**：

| 评审给的偏离方向 | ❌ 死板换措辞 | ✅ 大白话反向点出 |
|---|---|---|
| 维度偏 3D（应是 2D 扁平） | "杯子图标" | "扁平杯子" / "线条杯子" |
| 维度偏 2D（应是 3D 玻璃） | "勇气" | "立体玻璃勇气" |
| 媒介偏塑料（应是磨砂玻璃） | "文件夹" | "磨砂玻璃文件夹" |
| 配色完全错（应是粉色） | "猫" | "粉色小猫" |
| 主体形态完全错（不像主题） | "学校" | "学校建筑" |

**纪律**：和首轮一样的极简灵魂——不结构化、不堆叠风格词、只取**最关键 1 个反向锚点**。长度仍是 2-8 个中文字符为佳。

**B 档（标准）**——完全重写：
- 不含 `迭代` 字段（这是从头生成）
- 重新走 STYLE-CARD 字段映射 + 装饰元素三选一决策
- 重新写 `排除` 清单

```bash
node ~/.claude/skills/按图生/doubao-gen.mjs \
  --ref <原始参考图路径> \
  --prompt-a "$PROMPT_A_NEW" \
  --prompt-b "$PROMPT_B_REWRITE" \
  --theme "<theme>" \
  --round <round+1> \
  --auto-review
```

- `--ref`：**两档共用原始参考图**（与 v3.4 重写策略一致）
- `--round`：评审 push 进来的 round + 1

迭代后再次进入 Step 3.5 → 3.7 → 4 闭环。

## Step 5: 交付

评审 通过 后，**不直接放桌面**——先弹终稿确认浮窗，让用户看一眼成品拍板。

### Step 5.0: 终稿确认浮窗（必做，不可跳过）

```bash
RESULT="<temp_dir>/confirm-result.txt"
rm -f "$RESULT"
# confirm 走 open 异步拉起，命令立刻返回 → 必须轮询等 result 文件出现
~/.claude/skills/按图生/bin/confirm "<image_path>" "$RESULT"
# 阻塞等用户操作（点 OK 或点重做输入建议回车）
until [ -f "$RESULT" ]; do sleep 1; done
```

**铁律**：
- **必须**轮询等 `$RESULT` 出现再读，不得在 confirm 命令返回后立刻读（那时用户还没操作，文件不存在）
- **不得**绕过弹窗自己判定 OK 直接放桌面
- 弹窗内置跨 Space 浮窗 + 系统通知，用户在全屏 Space 也能感知；若长时间无操作就一直等

**读 `$RESULT` 第 1 行分流**：

| 第 1 行 | 自动执行动作 |
|---|---|
| `OK` | → 进入 **Step 5.1**（复制终稿到落点 + 交付话术） |
| `REVISE` | → 取**第 2 行**作为 `user_complaint` → 进入 **Step 4.1 双档迭代（修订）** |

**REVISE 分支接法**：
- 第 2 行（用户输入的建议）= 本轮修订的**最高优先级信号**，直接当成"评审最严重的 1 个问题"喂 A / B 档：
  - **A 档**：用户建议就是那句大白话方向（如用户说"留一层底板就好" → A 档 prompt 朝"带底板"方向加 1-3 词）
  - **B 档**：把用户建议填进 `迭代.调整` 数组的首条
- 第 2 行**为空**（用户点了重做但没输入文字）= 用户说"不行但没给方向" → 仍走修订，`user_complaint` 传空，A / B 档退回"换个方向重试"的常规修订逻辑
- 修订迭代后重新走 Step 3.5 → 3.7 → 4 评审闭环；**下一轮评审通过后会再次弹 Step 5.0 确认浮窗**（每次交付前都要用户拍板，不限轮数）

### Step 5.1: 复制终稿到落点 + 交付话术（仅 `OK` 分支）

1. **复制终稿到落点**——落点由入参 `交付落点` 决定（v6.7.0）：
   - **调用方传了 `交付落点`** → 复制到该路径（`交付落点` 已含目标文件名，调用方负责归置）；若父目录不存在先建：
     ```bash
     mkdir -p "$(dirname <交付落点>)"
     cp <image_path> <交付落点>
     ```
   - **没传 `交付落点`**（人工直接调用的默认）→ 回退桌面：
     ```bash
     cp <image_path> ~/Desktop/<theme>-终稿.png
     ```
2. **输出交付话术**——`<最终落点>` = 上一步实际写入的路径（`交付落点` 或桌面回退路径）：
   ```
   ✅ 生成完成！你已确认验收通过。
   终稿已保存到：<最终落点>
   临时评审文件保留在：<dirname(image_path)>（24 小时后自动清理）
   ⚠️ 此图为豆包产物，右下角含"豆包AI生成"水印——如需干净图，请 Read 一眼成品右下角确认，有水印就走「去水印」skill / remove-watermark.py 去掉（抠图可能顺带去掉、但不保证，仍需实测看图）。
   如需调整请告诉我具体方向。
   ```

   **水印提示的定位（v6.7.1）**：去水印是**交付后、由调用方决定的独立收尾关**，本 skill 只负责在交付话术里给出信号，**不在主流程内代跑去水印**（与抠图同一定位——工具独立、决策和执行权在调用方）。判据是「实际看图右下角还有没有水印」，**不是**「抠没抠图」——抠图可能顺带去掉水印但不保证（水印压主体/贴边会残留），所以无论抠没抠，交付前都要看一眼。

## 异常情况处理

| 场景 | 处理 |
|---|---|
| 参考图风格不明确 | 告诉用户"参考图风格特征不清晰，可能影响生成效果"，建议提供更典型的参考图 |
| 主题与参考图风格冲突 | 提示风格冲突，建议要么换参考图、要么调整主题适配 |
| CDP 连接失败 | 检查 Chrome 是否启动，手动 `--remote-debugging-port=9222` |
| Prompt JSON 不合法 | 用 `jq .` 校验后修正再 fire |
| 中文被 escape 成 `\uXXXX` | 用 `jq -c .` 重新序列化，禁用 `python json.dumps` 默认行为 |
| **双 tab 只成功 1 张** | 脚本自动降级为单图模式（仍是 `next_action: "main_pick_winner"`），主流程进入 Step 3.7 的单图分支直接当 winner，不做对比 Read。**不要**手动重启第二个 tab |
| **双 tab 全失败** | 脚本退出码非 0，主流程报错给用户、不重试 |

## 核心原则（Always）

1. **参考图驱动**：风格描述从参考图提取，不凭空想象
2. **双 tab 永远并行**：首轮 + 所有迭代轮，始终 A + B 双档
3. **A 档纯自然语言**：一句话大白话（首轮 2-6 字主题词；迭代时可加 1-3 词指向评审最严重 1 个问题，如"淡粉色的文件夹"）；绝不堆砌、绝不结构化、不写风格词、不用 JSON
4. **B 档完整中文 JSON**：沿用 v3.4 全流程，9 字段 + 装饰元素决策 + 排除清单
5. **winner 由主流程自主挑**：同回合并行 Read 3 张图（orig_ref + A + B），按宏观综合维度判，强制输出"两张观察 + winner + 一句话原因"
6. **评审权威**：评审 skill 是质量守门员，结论权威（形态评判关 Step C++ 已于 v6.4.0 删除，历史见评审仓 CHANGELOG）
7. **自迭代不打扰，但交付前必确认**：评审未通过自动迭代，连续 3 轮陷入相同问题循环才汇报，否则一直跑；**唯一会主动打扰用户的点是评审通过后的 Step 5.0 终稿确认浮窗**——用户看成品拍板 OK 才放桌面，点重做+输入建议则带着建议回 Step 4.1 修订
8. **B 档中文 JSON UTF-8 不可丢**：序列化必须用 `jq -c .` 或 `json.dumps(ensure_ascii=False)`
9. **Prompt 迭代 > 重拍参考图**：参考图稳定不变，调 prompt
10. **按需加载文档**：用到详细规则时再 Read 对应文档
