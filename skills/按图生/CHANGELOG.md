## v8.4.4（2026-08-18）根治豆包改版致输入框全线失配：textarea → Tiptap/ProseMirror contenteditable

**症状**：双 tab 生成 100% 失败、exit 8。日志诡异点在于**前半程全绿**——`textarea ready` 打印了、参考图上传成功、`thumbnail detected` 也有，偏偏卡在 `filling prompt` 之后 30s 超时，报 `[A] input box not found` / `locator.click: Timeout 30000ms exceeded waiting for locator('textarea[placeholder*="发消息"]')`。A、B 双 tab 各自重试一次也同样失败。

**根因（CDP 实测坐实，非推断）**：**豆包站点改版**，聊天输入框从 `<textarea placeholder="发消息">` 换成了 Tiptap/ProseMirror 的 `contenteditable` div（`div.tiptap.ProseMirror`）。连上真实页面探测 DOM：

| 选择器 | 匹配数 |
|---|---|
| `textarea[placeholder*="发消息"]`（脚本硬编码） | **0** |
| `div.ProseMirror` | 1，visible，位于页面底部输入区（y≈728） |

即选择器整条失配。**为什么日志前半程还是绿的**：`waiting for textarea to be ready` 那步的 `waitFor` 结果被 `.catch(() => false)` 吞掉后只做布尔判断，而上传参考图走的是 `+ 按钮` 坐标点击、不依赖输入框选择器——两者都绕开了失配点，于是失败被推迟到真正要 `click()` 输入框时才爆，日志读起来像"上传成功了却卡在填字"，误导性极强。

**改动**（`doubao-gen.mjs`，4 处）：
- 顶部新增常量 `INPUT_SEL`，用**逗号选择器同时兼容新旧两版**：`div.ProseMirror[contenteditable="true"], div.ProseMirror, textarea[placeholder*="发消息"]`。豆包若回滚到 textarea，脚本无需再改。
- 3 处硬编码 `'textarea[placeholder*="发消息"]'` 全部替换为 `INPUT_SEL`：`:281`（双 tab 预热等待）、`:314`（runOneTab 取输入框）、`:922`（runOneTabWithRetry 重试分支）。

**没动填值逻辑**：原以为 contenteditable 需要把 `fill()` 改成键入，读代码发现 `filling prompt` 段本就用 `keyboard.type()` 逐行敲 + `Shift+Enter` 换行（`:404-418`），对 contenteditable 天然兼容。故本次仅选择器一个点的改动，改动面小于预估。

**验证（端到端实跑，非仅语法检查）**：`node --check` 通过；真机重跑双 tab 生成，日志显示 `waiting for input box` → `uploading` 秒过（此前恒定 30s 超时）、`filling prompt` → `submitting` → `waiting for new images` 首次越过历史死点，A/B 双 tab 均成功提交进入出图。

**回退**：`git checkout v8.4.3 -- doubao-gen.mjs`。

## v8.4.3（2026-08-12）A 档 prompt 统一补指令前缀「帮我按照参考图，生成」

**动机**：A 档（极简档）此前发给豆包的是纯主体大白话（`一支铅笔`），没有任何指令动词，依赖豆包自己意识到「上传的参考图是风格锚点、文字是要画的主体」。加一句显式指令前缀，把「按参考图生成」这层意图挑明，减少豆包把裸主体词当成搜索/追问的歧义。B 档（JSON 标准档）不受影响。

**实现层选择（脚本层，不是文档层）**：前缀写在 `doubao-gen.mjs` 的 PROMPTS 构造处，而非要求主流程写 prompt 时自己带。原因：SKILL.md 里 A 档写作规则散在 3 处（Step 2 首轮 / Step 4.1 修订 / Step 4.1 重生成）+ 十几个范例表格，靠主流程自觉逐处带前缀必漏，且漏了不报错、只会静默产生两种口径。放脚本层则首轮 / 修订轮 / 重生成轮三条路径自动全覆盖。

**改动**：
- `doubao-gen.mjs`：新增 `A_PREFIX` + `withAPrefix()`，仅作用于 dual 模式的 A 档；已带前缀的原样透传，避免重复拼接。单 tab 兼容模式的 `--prompt` 与 B 档均不动。
- `SKILL.md` Step 2 A 档写作纪律：加一条说明「前缀由脚本自动补，主流程只写主体大白话、别手写前缀」。

**语义提示**：迭代轮 `--ref` 传的是上轮 winner 而非原始参考图，此时前缀里的「参考图」指向上轮结果——豆包眼里看到的确实就是那张，语义成立，但读日志时需知道这个指向差异。

**验证**：`node --check` 语法通过；三组拼接用例实测 `一支铅笔`→`帮我按照参考图，生成一支铅笔`、`淡粉色的文件夹`→带前缀、已带前缀者原样透传。未跑端到端生成。

## v8.4.1（2026-08-08）根治「新 tab 秒判 textarea 没出现 exit 5」：isVisible({timeout}) 从不等待

**症状**：双 tab 首轮生成高频失败，日志 `[A] textarea did not appear within 45s` → exit 5。诡异点：用户每次切到自动化 Chrome 看，豆包页面**完全正常、输入框就在那**——"总是失败但看着没问题"。

**根因（官方文档坐实，非猜测）**：Playwright 的 `locator.isVisible({ timeout })` **不等待**——timeout 参数被官方标记为 ignored，元素未渲染时立即返回 false。脚本用 `isVisible({ timeout: 45_000 })` 等新 tab 的 React 初始化，实际是 goto 后 ~2s 就秒判失败退出；用户随后看页面时早加载完了，所以永远复现不了"坏页面"。只有复用已 ready tab 时才侥幸通过——这解释了"总是遇到"却时好时坏。

**排查时的干扰项（记录备查）**：手动 `connectOverCDP("http://localhost:9333")` 诊断时报 400——是 shell 的 `HTTP_PROXY`（无 NO_PROXY）把 localhost CDP 请求发给了远程代理；加 `NO_PROXY=localhost,127.0.0.1` 即通。脚本自身用 node fetch 直连不受影响，此项与本 bug 无关，但排查同类问题时先排除它。

**修复**：doubao-gen.mjs 全部 7 处 `isVisible({ timeout: N })` 改为 `waitFor({ state: "visible", timeout: N }).then(() => true).catch(() => false)`——含 3 处 textarea 等待（主流程双 tab / runOneTab / retry 路径）+ 1 处图像生成按钮探测 + 3 处 submit 按钮降级链。

**验证**：修复后实跑一轮——新 tab goto 后 textarea 2s ready，双 tab 全成功，21~26s 出图，2848×1600 原图落盘，评审一次通过。

**回退**：仅改 doubao-gen.mjs，`git checkout v8.4.0 -- doubao-gen.mjs` 即回退。

## v8.3.0 → v8.3.2（2026-07-28）根治「打不开豆包 / 看不见窗口 / 一口气开一堆 tab」

**症状链**：用户调用按图生 → 豆包打不开、第一轮 150s 超时空转、产物目录恒空、用户在自己浏览器里看不到任何窗口。

**根因（进程实况坐实，非猜测）**：脚本写死连 CDP 默认端口 `9222`。但 9222 是 Chrome DevTools 全行业默认口，被另一个项目（xiaoya3）遗留的 `cp-nav` 导航 **headless** Chrome（只开着 `about:blank`）先占了。旧逻辑只探测「9222 有没有人在听」、**不校验听的是不是自己的豆包实例**，于是盲连到那个隐形空壳页——用户看不到窗口、也永远等不到出图。

**v8.3.0 三处改**：(1) 端口 9222 → 按图生专属 `9333`（`--port` 可覆盖），物理隔离；(2) `spawn` 时显式 `--new-window` + 直接打开豆包 URL，强制有头可见（满足用户硬要求：每次跑豆包必须能亲眼看到）；(3) 连上后校验实例身份，非自己的实例才杀端口重启。同步把自愈 pkill 的匹配串跟随 `DEBUG_PORT`。

**v8.3.1 修正 v8.3.0 引入的回归**：v8.3.0 的实例校验用了「新开 tab → goto 豆包 → 关掉」的重手段，两个错——① 脚本后面本来就要开豆包 tab 干活，探测 tab 白开还占加载时间；② 拿「一次 goto 超时」当「连错实例」判据太激进，豆包首次加载偶发慢就误判、触发杀实例重启+再开 tab，表现为「刚打开豆包却不用、非要另外再开俩」。改成**零成本轻量校验** `isOurInstance()`：只查①现有 tab 有无豆包域名 ②`/json/version` 的 userDataDir 是否为 `~/.chrome-automation`，不打开任何页面，加载慢交给后续 goto 自己重试。

**v8.3.2 收尾占位空首页**：为保证有头可见，启动时 `--new-window` 开的豆包首页 tab 不参与生成（干活的是 A/B 认领 tab），白占一格。干活 tab 备齐后自动关掉「不在 pages 里、且 URL 精确等于豆包首页（`chat/` 结尾无会话 id）」的占位 tab。判据收紧到精确匹配首页——进入对话的 `/chat/<id>` 及用户手动开的别的豆包对话 tab 不会被误关。**A/B 双 tab 是核心质量机制，保留不动**；被清的只有启动占位的那个空首页。

## v8.2.2（2026-07-28）根治 observer 白等 150s：横向 banner 缩略被 rect 门槛差 1px 误伤

**来源**：v8.2.1 后实测发现——虽然图最终能抓到，但 observer 主路径**每次都白等满 150s、靠退出前 rescan 兜底才捞到**（图其实很早就渲染了）。加诊断日志定位根因。

**根因（诊断确认，非猜测）**：observer 的 `tryRecord` 有个 `rect.width < 100 || rect.height < 100 → 拒` 的门槛，本意排除小图标/占位符。但**横向 banner 缩略的渲染尺寸是 361×99**——height 99 < 100，**差 1 像素被拒**，observer 直到超时都没记到它；而 rescan 不看 rect（只看 naturalWidth ≥256）所以能兜底捞到。诊断日志实锤：`observer saw 2 rc_gen_image(s) but rejected: [..., "rect-too-small(361×99) :: .../rc_gen_image"]`。方形/竖图不触发（高度够），只有宽扁 banner 中招。

**修复**：rect 门槛从 `width<100 || height<100` 改为**「较长边 ≥100 且较短边 ≥60」**——既放行宽扁 banner（361×99 通过），又仍排除真正的小图标（两边都小）。

**附带保留**：v8.2.1→v8.2.2 排查时给 observer 加的**拒因诊断**（`in-baseline` / `not-complete` / `naturalW<256` / `rect-too-small` 分类记录，timeout 时 dump），是定位本 bug 的功臣，保留供未来排障——顺带把内层 `reject` 改成统一 `resolve({ok, results, rejects})`，外层据 `ok` 判超时。

**验证**：修复后 observer 主路径**提交→抓到图仅 21s（A）/ 26s（B）**，日志不再出现 `observer timeout` / `running final rescan`——图一渲染就即时捕获、立刻下载。对比修复前每次白等 150s。下载仍为 4096×1120 真生成图，Read 确认非参考图。

**回退**：仅改 doubao-gen.mjs，`git checkout v8.2.1 -- doubao-gen.mjs` 即回退。

## v8.2.1（2026-07-28）修正 v8.2.0 回归：回捞放宽白名单会把参考图错当生成图

**来源**：v8.2.0 发布后实测验证，发现引入了一个比原 bug 更危险的回归——**rescan 回捞把用户上传的参考图错当成品捞回下载**。

**回归根因**：v8.2.0 为"多抓一些"，把主检测的 `isFallbackGen` 和 rescan 的候选筛选放宽到 `byteimg/byteacctimg/imagex/tos-` 泛 CDN（只要 ≥512px）。但**豆包给用户上传的参考图也走 byteimg CDN**——页面上那张 1209×330 的参考图缩略正好落进网，被当成"最大的新图"捞走。实测日志：`rescued 1 image(s)（largest 604×165）` → 下载得到 `1209×330, 98797 bytes`，正是参考图本身。这比原"漏抓"（保守失败）更坏：把错图当成品静默交付。

**修正**：
- 撤掉主检测的 `isFallbackGen` 泛 CDN 匹配，恢复为**只认 `rc_gen_image`（或 blob:）**——这是豆包生成图的稳定标识，参考图永不含此路径段，是唯一可靠判别锚。
- rescan 候选筛选同样收紧为**只认 `rc_gen_image` / blob:**，阈值回 256。若真没出图，rescan 找不到候选 → 正确 throw（而非错抓参考图）。

**保留 v8.2.0 的正确部分**：内层窗口 `GEN_WAIT_MS=150s`、外层 evaluate 不被默认 30s 腰斩、退出前 rescan 兜底 + 诊断日志——这三项没问题，继续保留。

**验证**：修正后连跑两次 B 档（长 JSON，最易触发 rescan）——rescan 捞到 `384×105` 缩略 → hi-res 下载 `4096×1120, 3.3MB` 真生成图（玻璃卡片叠层+版权盾徽章），Read 确认非参考图。两档均正确。observer 内层仍 timeout、由 rescan 兜底救回，证明兜底路径本身有效。

**回退**：仅改 doubao-gen.mjs，`git checkout v8.2.0 -- doubao-gen.mjs` 即回到（有回归的）v8.2.0。

## v8.2.0（2026-07-28）修复 doubao-gen.mjs「豆包出图了却判 captured 0」的抓图缺陷

**来源**：一次 banner 重生实战，B 档（700 字 JSON prompt）在豆包页面里**确实渲染出了生成图**（用户截图为证），但脚本判 `captured 0 images` 降级单图。排查出图片检测环节四个叠加根因，全部修复。

**根因一（主因，最隐蔽）：外层 `page.evaluate` 默认 30s 超时腰斩内层**
- 内部 observer 写了等 45s，但 `page.evaluate()` 不传 `timeout` 走 Playwright 默认 30s，先抛 `page.evaluate: Error: timeout at <anonymous>` 把内部 promise 掐断——日志里那行 `<anonymous>:17:60` 就是它。内层想等 45s，外层 30s 就腰斩了，出图了也判 0。
- 修复：内层窗口提为常量 `GEN_WAIT_MS = 150_000`，由内层自管超时；不再依赖被默认值腰斩的外层。

**根因二：检测窗口太短**
- 45s 对 B 档（长 JSON，推理+排队更慢）不够。拉长到 150s。

**根因三：白名单过严漏判**
- `isGenSrc` 只认 `rc_gen_image` / `blob:`，别的 CDN 路径的生成图永远 record 不到。新增次级兜底 `isFallbackGen`（byteimg/byteacctimg/imagex/tos-），但要求 `naturalWidth ≥ 512` 排除参考图缩略误判（参考缩略 ~289）。

**根因四：失败即 throw、无退出前回捞**
- 内层空手就直接 throw → 立即新开 tab 重试，丢掉原 tab 里马上要出的图。新增「退出前最终 rescan」：在**原 tab**上扫已渲染的新大图（≥512），捞到就用；没捞到 dump 前 12 张 img 的尺寸+src 诊断日志，区分「真没出图」vs「出了没抓到」。

**连带**：内层返回变量 `images` → 兜底后统一为 `capturedImages`，同步下游 `targetId` 提取与 `fetchViaCtx` 两处引用。`node --check` 通过。

**回退**：仅改 doubao-gen.mjs，`git checkout v8.1.0 -- doubao-gen.mjs` 即回退。

## v8.1.0（2026-07-28）两处发散/填卡加固：用户诉求 vs 评审锚点冲突 + 实心图标内部留白镂空

**来源**：一次「按参考图生成汽车」实战，6 轮才收敛，暴露两个规则漏洞，分别加固进 SKILL.md Step 4.1.0 与 STYLE-CARD.md 填充模式段。

**漏洞一：用户诉求删的载体 = 评审的风格锚点 → 死循环（SKILL.md Step 4.1.0 特例）**
- **现象**：参考图是"双层错位方块 app 图标（前蓝紫渐变方块 + 后黑错位方块 + 白描边 Σ）"，用户 REVISE 明确"去掉这两个方块，整个画面都是车"。但**方块正是评审拿原图当锚认定的风格骨架**。于是"删方块"这个动作 → 评审锚点仍含方块 → 连续 2 轮（删方块做纯剪影车、删方块做等距色块车）都被判「同风格=否/重画」，撞死循环。
- **根因**：老的发散关反例都是"评审自己报的问题"（外框冗余→删框丢主导色），没覆盖"**用户要删的正是评审的锚点**"这一类——冲突双方是用户 vs 评审，直接顺任一方都错。
- **正解（用户点破）**：保留**构图形式**（层叠 / 错位关系 = 评审骨架），只把**载体形状**换成主题元素（方块 → 车）：前层蓝紫渐变车 + 后层黑色错位车影 → 层叠 DNA 在（评审过）+ 画面全是车（用户满意）。一轮通过。
- **加固**：Step 4.1.0 第 3 步「第三条路」下新增 V5.8 特例——识别"用户删的载体是否扛构图语言+主导/次要色"，强制"分开构图形式与载体形状、只换形状保住形式"，`迭代.保持` 显式钉构图关系；穷尽第三条路仍不行才升级 Step 4 收敛兜底让用户在"关评审"和"保骨架"间拍板。

**漏洞二：实心图标的内部留白镂空易被填死（STYLE-CARD.md 填充模式段）**
- **现象**：参考图 Σ 是"实心方块内挖出白色镂空线条"；生成汽车时第 5 轮（评审已通过）把前车做成一整块纯蓝紫实心剪影、**车窗填死无镂空**，丢了"实心色块 + 内部留白挖空"的关系。用户"参考图中留白的部分呢？"打回，第 6 轮把车窗做成镂空留白才补上。
- **根因**：填卡只记 `实心填充`、没记"内部有镂空留白"；豆包默认倾向把实心内部填死。
- **加固**：填充模式段新增"实心/混合填充也要查内部留白镂空"——填卡时盯主体内部有无透底镂空、有则显式写明；B 档 prompt 必须点出"主体实心 + 内部 XX 镂空留白"并在 `排除` 列"实心填死的车窗/内部"。

**回退**：本次仅改 SKILL.md + STYLE-CARD.md 两个 md，无脚本改动，`git checkout v8.0.0 -- SKILL.md STYLE-CARD.md` 即回退。

## v8.0.0（2026-07-27）颠覆性升级：评审移出主上下文 → 独立进程一句话宏观评审

## v7.2.0（2026-07-27）宏观快筛前移为「裸眼直觉」独立进程（治文档负担钝化直觉）

**翻车现象**：v7.1.0 把宏观快筛写成评审 SKILL.md 的 Step 0，于是它必然发生在"进程已 Read 两份评审文档（SKILL.md + REVIEW-DISCIPLINE，~44k token）之后"。用户实测：同两张明显不同风格的图（纯黑粗描边实用图标 vs 淡紫渐变柔和氛围装饰），**带文档的进程草率答「是」→进完整流程**；而另开一个啥都没加载的干净窗口纯问「属于一个风格吗」→中肯答「否」+7 维度对比。结论：**一大堆评审纪律文档把模型框进了"完整评审流程"的惯性，钝化了第一眼直觉的诚实度。**

**修正（评审仓 `review-headless.sh` 改两段式）**：

**收益**：宏观快筛拿到最锋利直觉（不再放水）；大量"一眼不对"的图在第①段极快出局，省文档加载 → 又快又准。

## v7.0.0（2026-07-27）评审移出主上下文 → 独立 `claude -p` 进程（根治同上下文放水）

**背景（翻车根因）**：评审一直在主生图 CC 窗口的**同一上下文**里跑（无论 Skill 调用还是循环卡直评）。同一上下文里评审自己刚生成的图会**天然放水**——主流程带"想让自己的图过"的隐性动机，所谓 fresh-eyes 是伪的。用户实测：同一个评审 skill，在生图流程窗口里跑 vs 另开一个干净 CC 窗口跑，严格度完全两样。曾试过 subagent，但 subagent 拿不到真实像素、会**幻觉**（编图内容）。

- 脚本 stdout 末行输出握手 JSON `{"status":"ok","result_path":...,"round":N,"child_exit":0}`，主流程解析后 Read result_path 拿结论

**验证证据**：同两张图，老的同上下文评审判「通过」，独立进程 fresh-eyes 判「修订」——放水被根治。轮次不喂给评审进程（`推送载荷.轮次` 为 null），fresh-eyes 铁律守住。

## V5.3.2 加法发散

**背景**：之前的发散动作清一色是减法/挪移（删元素、转移载体），从没考虑过引入新元素——把"发散"窄化成了"只在现有元素上动刀"。但参考图本身就是「主体 + 配件 + 叠层」一组元素；新主题下完全可以引入符合风格、又服务主题的新元素（如头像玻璃光环、薄荷绿氛围光点）。

## V5.3.1 DNA 抖落

**翻车案例**：删「圆角矩形玻璃底板」那轮，只查了「颜色」（深墨绿/薄荷绿/白玉都在别处）就放行——没查「厚玻璃板的体积折射质感」「叠层结构」这两个非颜色特征。删完底板，这两个特征没有别的载体接，终稿里厚玻璃质感弱化、叠层消失。

**根因**：把「风格不变量」窄化成当下盯着的那一个维度（先窄成枚举字段、再窄成具体形状、又窄成颜色）。解法不是再加"质感必查/结构必查"的封闭清单（永远漏下一个），而是**开放穷举**：对着要删的载体把它身上所有可指认的特征全抖出来，逐项确认有没有别的载体接住。正确做法本应是：抖落时列出底板扛着「颜色 + 厚玻璃折射质感 + 叠层」，发现后两个没载体接 → 把厚玻璃片质感转移到主体剪影上。

## V5.3 发散关（Step 4.1.0）

**翻车案例**：评审 Step C+ 报「深蓝外框冗余」，直接翻译成「删框」执行；但参考图的深蓝黑是**主导色**，删框 = 丢主导色 = 风格不一致。「满足交付（删框）」和「保持风格（留深蓝黑）」死磕成二选一。

**规则**：评审给的是「问题描述」不是「唯一解法」。写迭代 prompt 前必须在解空间发散一步，找兼顾冲突双方的第三条路（如「去框 + 深蓝黑转剪影描边」）。边界：只在兼顾本次冲突范围内，不改主题。
