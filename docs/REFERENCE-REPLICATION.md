# 参考元素复刻规范

本文档定义了使用 liaison「找参考」功能复刻线上参考元素时的强制工作流，用于规避"观察准确但执行偏差"的典型失误。

---

## 问题根源

**现象**：观察参考时理解清楚（线框图标注准确），但写代码时凭印象执行，导致：
- 数字偏差（线框图写 220px，代码写 100%）
- 交互缺失（参考有 hover 效果，代码做成静态）
- 行为误判（参考是 hover 滑入，理解成了常驻显示）

**根本原因**：人类设计师复刻时眼睛和手是同步的（边看参考边写代码）；AI 执行时"观察"和"执行"容易脱节——观察阶段输出了准确的线框图，但执行阶段没有回头对照，直接凭印象写。

---

## 最高原则：完全复刻时，参考对象是唯一标准，不再自由发挥

**用户要求"完全复刻 / 尽量 1:1 还原参考"时，采集件（computed style / 内部结构 / 视觉资源等采集数据）就是唯一事实源。参考给了明确值就照抄——是 0 就写 0，是 8 就写 8；参考没有的间距 / 样式，不许无中生有地补。**

这条统管全篇：下面所有具体纪律（间距预算、尺寸适配、装饰留白……）都只在"参考没覆盖到的空白处"才生效，不许拿它们去**盖掉**参考已有的真实值。

### 照抄采集值时，必须连它依赖的上下文一起抄——单值不成立（治"逐属性都抄了却不像"）

**一个采集值往往不是孤立生效的，它依赖采集件里另一处数据当"基准 / 衬托"。只抄这个值、丢掉它依赖的上下文，等于把值搬到了不同语境里——语义漂移，属性对了但合成效果错。** 复刻不像的第二大来源就是这个（第一大是拿设计经验盖真实值，见上）。这不靠事后"看成品像不像"的主观自检去兜底（AI 自检不可信，又当运动员又当裁判）——靠**照抄时就把上下文抄全**这个客观动作从源头堵。

抄任何一个值前，先问一句"**这个值依赖采集件里的哪条其它数据？依赖的那条我抄了吗？**"三类高频依赖必须成组抄，不许拆成孤立单值：

1. **相对值 ⟷ 它的基准尺寸**：抄子元素的 `flex` / `flex-grow` / `flex-basis` / `%` 宽高时，采集件给的**父容器 `width`/`height`** 必须一起落地。`flex:1` 在"父宽 300px、4 等分"和"父宽 590px、4 等分"里是**两种完全不同的结果**——脱离父尺寸约束，相对值就漂了。（反例见下：抄了 `flex:1` 丢了父 `width:300px`，格子在 590px 卡里被拉宽、间距撑开。）

2. **本体 ⟷ 它的伪元素 / 相邻装饰**：采集件里同一元素的 `::before`/`::after`、内联 SVG 的 `fill`、以及紧邻装饰元素的颜色，要**连起来读成一个视觉单元**，不能各抄各的。一个 `fill:#fff` 的白三角 + 一个 `rgba(247,122,49,.3)` 的橙描边框，合起来才是"靠橙框衬托、被咬出缺口的尖角"；把白三角单独抄到白底上 = 白盖白、直接隐形。（反例见下。）

3. **子元素 ⟷ 父级布局属性**：子元素的 `align-self` / 定位 / `margin` 负值，常依赖父级的 `display:flex` + `align-items` / `justify-content` / `position` 才成立。抄子不抄父的布局语境，子元素的定位就落空。

> 💡 **反射触发**：写每个相对值 / 装饰值前，回采集件确认它的"依赖项"抄全没有——这是**可核对的客观动作**（采集件里有没有那条数据、我落地了没有），不是"我觉得像不像"的主观判断。源头抄全，比事后截图自检可靠。

**反例（2026-07-29，本规则来源，同一次复刻踩两个）**：复刻知乎「连续激励进度条」——
- **尖角隐形**：采集件给了小三角 SVG `fill="#ffffff"` **和**同元素 `::before` 橙描边 `rgba(247,122,49,.3)`，两条数据都在。但当成两个无关属性各抄各的，只把白三角画到白底上 → 白盖白隐形。合起来读才知道三角靠橙框衬托。
- **间距撑开**：采集件给了根容器 `width:300px`，子元素 `flex-grow:1 flex-basis:0%`。只抄了 `flex:1`、丢了父 `width:300px` → `flex:1` 在 590px 目标卡里把 4 格拉宽、间距撑开，和参考"格子挤在 300px 里"完全不同。
- **共同根**：不是没看采集数据，是把采集数据拆成孤立单值照抄、丢了值与值之间的依赖关系。

### 抄 position + 偏移前，先推演它占不占位、会不会挤邻居（治"内容被水印挤偏"）

采集件逐节点列 `position` / `top·right·bottom·left`，但**不会告诉你两个子元素是"重叠两层"还是"上下堆叠"**——这个关系要你从定位值自己推。抄定位值时，先在脑子里跑一遍布局，判断：

- **relative**：元素**仍占文档流**，`top/left` 只是视觉移位、**原位置照样占高/占宽** → 它会把后面的兄弟往下/往右挤。
- **absolute**：元素**脱离文档流**、不占位 → 叠在别人背后/上面，不影响兄弟排布。

**别凭 `background-image` 就臆断成"垫在文字背后的重叠水印"。** 先分清参考到底是「上下堆叠」（数字在上、文字紧接其下，各自占位）还是「重叠两层」（数字垫在文字背后）——这决定用 relative（堆叠）还是 absolute（叠层）。**拿不准就按上位规则「该量不估」去量**：量参考里各子元素相对卡片的真实 `top`/`height`——若首尾相接（如 num `top17,h32` → intro `top32,h74`）就是**堆叠、保持 relative**；若 top 区间重叠才是叠层、用 absolute。

> 💡 反射触发：抄任何 `position` 值前问两句——"它占不占位？参考是堆叠还是重叠？"拿不准就量，别估。

**反例（2026-07-30，本规则来源，连错两次的完整教训）**：复刻百象亮点卡 `card-num`（大数字），采集件给 `position:relative · top:17px · bottom:-17px`。
- **第一错**：照抄 relative 后觉得"数字把文字挤下去了"，就**臆断它是垫背后的水印、改成 absolute**——其实方向本来是对的。
- **第二错**：改 absolute 后**估坐标**（`中心+17px`），落到标题下方；再估 `top:20px`，还是不对。
- **实测才真相大白**：量得 `num(top17,h32)` + `intro(top32,h74)`，**top 首尾相接 = 本就是正常上下堆叠**，数字 relative 占位在上、文字接其下、整组靠 flex 卡内居中。原样 relative:top17 才对，我把对的改错、又估了两轮。
- **双重根因**：① 把"堆叠"误判成"重叠水印"（凭 background-image 臆断）；② 该量的坐标去估（违反「该量不估」）。

### ⚠️ 与采集件注入的「设计决策纪律」的优先级（关键，治根性翻车）

liaison 采集件每次会在 prompt 里注入一段 **`# 设计决策纪律`** + **`## AI 视觉反套路清单`**，里面是"原创 / 发散设计"口吻的经验，典型如：

- 「间距优先……先列出每对相邻元素的**最小呼吸预算**（title↔body≈4~6px，body↔cta≈10~12px，装饰↔容器边≥8px）……**绝不压间距**」
- 「**装饰元素不贴容器边**……三条边各留 ≥ 8px 呼吸……必要时给装饰图**加小圆角让它更精致**」
- 「**按钮到正文必须有显式间距**……给按钮显式 `margin-top: 10~12px` 作为**最小呼吸兜底**」
- 排版精致度：大标题加负字间距、阴影带主色调、不对称留白……

**这套经验的定位是"原创设计时主动补呼吸 / 提精致度"，它默认的场景是发散设计，不是复刻。** 复刻模式下它的优先级**低于采集数据**：

| 场景 | 谁是主导 | 采集数据的角色 | 那套设计纪律的角色 |
|---|---|---|---|
| **原创 / 发散设计**（改风格、加模块、"出几版"） | 设计经验主导 | 参考 / 灵感 | 主动生效，该补呼吸就补 |
| **1:1 完全复刻**（"复刻这个""尽量还原参考"） | **采集数据主导（唯一标准）** | **唯一事实源，照抄** | **退到只在采集没给值的空白处才补位；不许盖真实值** |

**判据只有一个**：用户说的是"复刻 / 还原 / 照着做" → 走复刻模式，采集值优先，那套呼吸/兜底经验整体让位。

### 这是"类别错误"，不是单点属性错误——所以只立一条总则，不逐属性打补丁

翻车的根不是"margin 记错了"，而是**把原创设计经验套用到了该纯照抄的复刻场景**。margin 只是症状，padding / 字重兜底 / "装饰加小圆角更精致" / "按钮 margin-top 兜底" 全是同一个病——拿设计经验盖了参考真实值。**所以不为 margin / padding / 字重逐个加补丁**（那样只会堆出一堆散乱、互相打架、更难找的单点规则）；只立这一条上位判据，一条顶掉所有单点。

> 💡 **反射触发**：落地写每个 self 属性（margin / padding / 字重 / 圆角 / 间距）前，先问一句——"采集件里这个值是多少？"有值照抄，没值才允许用设计经验补。**绝不用"该给点呼吸"的直觉去覆盖采集里的明确值。**

**反例（2026-07-29，本规则的来源）**：复刻知乎话题卡，参考正文 `p.css-1e6ezdb` 的 `margin` 采集值是 **0**（间距由作者行的 `padding:10px 0 0 0` + flow-root 块级流承担）。但落地时套用了采集件「按钮/正文该给 margin-top 兜底」的经验，擅自给目标正文写了 `margin: 8px 0 0`——凭空多出参考里不存在的 8px。根因：把"补呼吸"经验的优先级放到了采集真实值之上。

### 同一类别的第二个变体：用「目标项目已有的相似实现」盖掉参考真值

上面讲的是**设计直觉**盖真值。还有一个同类、但更隐蔽的变体：**目标项目里已经存在一个"看起来也对"的现成实现**时，它会悄悄取代参考、成为事实基准。

**为什么更隐蔽**：它有正当外衣。"保持项目一致性"、"复用已有视觉语言"、"沿用同源写法"——这些在原创设计里都是对的，所以不会触发自我怀疑，甚至会被当成优点写进注释里。而"设计直觉盖真值"至少还知道自己在发挥。

**真实翻车（2026-08-20，本规则来源）**：复刻一个 Tab 项，采集件明确给了 `line-height: 28px` + `padding: 4px 0 0` + 文字与短杠间距 0。动手前 grep 目标项目，发现顶部已有一套"一模一样"的 Tab 栏（36px 行高 + 4px gap），于是决策重心从**抄参考**滑向**对齐项目已有实现**，写成了 `line-height: 36px` + `gap: 4px`，还在回复里主动声明"沿用同一套视觉语言"当作优点。盒高比参考高 8px、短杠被推远。**采集数据没被漏读，是被降级成了"验证材料"而不是"施工图"。**

**硬规则**：

- **参考给了显式数值的属性，必须逐条落到代码里。禁止用"项目里已有类似组件"的值代替。**
- 发现目标项目有相似实现时，它**只可用于确认变量名、写法惯例、类名规范**——**不得用它的数值覆盖参考数值**。
- 两者数值冲突时**以参考为准**，并在改动要点里单独列出冲突项让用户裁决。不许静默选一个。

> 💡 **反射触发**：每写一个数值前问一句——"这个数字是采集件给的，还是我从项目里抄来的？"答不上来 = 停下来回查采集件。

> ⚠️ **为什么朴素 HTML 里很少翻车**：不是那里样式简单，是**那里没有竞争性答案**。参考是唯一信息源，只能照抄。复杂项目里多出来的干扰不是"样式复杂"，而是"存在一个看起来也对的替代答案"。所以**越是成熟项目、越是有现成同类组件，越要逐条对账**。

## 核心原则：参考图的总尺寸是结果，不是约束

复刻 / 改造 UI 时，看到参考图标注"330×218"、"宽 288"、"高 124"这种**总尺寸**数字，**先问自己一句"这是结果还是约束"**。99% 的情况下是**结果**——参考的总尺寸是 padding + 内容 + 各级间距**自然撑出来的**，不是设计师拍脑袋设死的硬规约。

### ❌ 禁止做的事

- 给目标元素直接设 `height: 218px` 或 `min-height: 218px` 来对齐参考总高
- 配合 `flex: 1` / `flex-grow: 1` / `margin-top: auto` 让某个子区域吃掉多出来的空间——这种组合等价于"硬塞总高 + 让子区压/撑内容凑数"，是反向操作

### ✅ 应该做的事（间距优先、尺寸适配原则）

1. 先列出**每对相邻元素的间距预算**（如 header padding-top 28 / 标题→标签 12 / 标签→header padding-bottom 20 / desc padding 18+22）
2. 累加 padding + 内容固有高度 → 算出目标卡的**自然高度**
3. 让卡片由内容自然撑高，**不要 min-height 硬塞**
4. 如果算出来高度和参考差几十 px，**接受这个差异**——内容长度不同必然不一样，强行对齐反而扭曲

### 何时可以指定固定高度

- 父容器明确要求所有子项等高（如 grid 的 `align-items: stretch`，但 liaison 场景通常是 `align-items: start`）
- 内容是**已知固定的**（如 hero banner 设计稿要求精确 600px 高，且内容刚好填满）
- 这两个场景实际很少见——大部分卡片 / 列表项 / 信息容器都不该设固定高度

> 💡 **反射触发**：「具体数字 > 抽象原则」是 AI 执行 UI 任务时的典型反射陷阱。下次看到任何参考图的总尺寸数字时强制触发反射："这是结果还是约束？"

## 同库参考：复用优先于复刻（结构性防漂移）

**判定**：参考 URL 命中当前项目（localhost / 同域生产环境）→ 参考组件的源码就在本地代码库里。此时**禁止**像对外站一样逐值手抄——手抄必然漂移（见案例 #4：图标字形、8/12px 间距、规则覆盖三处全漂了）。

处置优先级（从高到低，只有上一级不可行才降级）：

1. **直接复用**：公共 class / 抽 mixin / 两个组件引用同一段 less
2. **整块拷贝**：把参考的规则块整体拷过来改选择器——值成套迁移，不会漏掉块内的覆盖规则
3. **逐值手抄**（最后手段）：每个值必须验证是"最终生效值"（见下方 Diff 表纪律）

**Why**：一源多用，值就不可能不一样；两源手对，漂移只是时间问题。

## 强制 Checklist（写代码前必过）

### 0. 📋 子元素逐项 Diff 表（线框图之后、动代码之前必产出）

**操作**：对参考里每个**可见子元素**（图标、标签、计数、链接、光标、hover、动效）建一行，逐项对比：

| 子元素 | 属性 | 参考值（来源） | 目标现状 | 处置 |
|--------|------|--------------|---------|------|
| 计数图标 | 字形 | antd like filled（HTML） | iconfont 点赞面 | 复刻 |
| 计数项 | 间距 | 12px（computed 实测） | 16px | 复刻 |

**两条硬规则**：

- **"保留"必须写理由；写不出理由 = 默认复刻**。"目标业务自带所以不动"不算理由，要写清为什么该子元素不在视觉复刻范围内。消灭"默认保留"暗区
- **数值只认 computed / 浏览器实测**。读源码只用于理解"值由哪条规则产生"；引用源码值之前必须检查同文件是否有更高优先级的覆盖规则（`:nth-child` / 更长选择器 / `!important`）。采集数据没覆盖的深层子元素，宁可去浏览器量一次 computed，不凭"第一条命中的规则"下结论

**检查点**：

- ✅ 线框图里每个小部件（计数器、图标组、标签）都有字形来源和间距数值标注——没有数字的地方 = 没有验收标准
- ❌ 反例：线框图画了 `♥1 💬1 👁15` 但没标图标用哪套、项间距几像素 → 执行时凭目标现状保留 → 用户逐个指出返工

### 0.2 ⚠️ B 自适应模式：每一处偏离参考都必须显式声明

B 模式给了发挥空间，而**"有意的自适应"和"抄错了"在事后无法区分**——任何偏离都能事后编出一个场景理由。所以：

- **每一处偏离参考数值的地方，必须在改动要点里单独写一行**：`⚠️ 偏离：<属性> 参考 X → 目标 Y，理由 Z`
- **没写出来的偏离 = 错误**，不是"自适应"。
- 这条规则的真正价值不在于告知用户，而在于**它逼你在每个数值上问一次"这是参考给的还是我编的"**——上面那个 28→36 的翻车，正是因为当事人以为自己在抄，压根没意识到偏离发生了。

### 0.3 🎨 Token 映射：以目标项目的设计系统为第一准则

目标项目若接入了设计系统（token / 语义变量），**参考的裸值必须映射成 token 再落地**，不许直接写字面量。

**这条和上面「禁止用项目已有值代替参考值」不矛盾，边界是**：

| 规则 | 管的是 |
|---|---|
| 禁止用项目既有实现的值代替参考值 | **值从哪来** —— 参考说 28，不许因为项目里有个 36 就写 36 |
| Token 映射 | **值怎么写** —— 参考说 28，项目 token 里有个 28 的档位，那就写变量名而非字面量 |

前者防**数值被替换**，后者要求**表达方式被替换、数值不变**。

**优先级链：语义层 → 基础层 → 就近滑档 → 保留原值**

1. **先在当前项目里定位设计系统 token 定义**（grep / 看项目 CLAUDE.md），建立「值 → 变量名」反查表。**不要凭记忆猜变量名**，也不要假设项目一定接了设计系统——找不到就退回保留参考原值，这是合理行为。
2. **语义层整组匹配优先**。字体的 `(字号, 行高, 字重)` 常被打包成一个复合令牌（如 `font: 600 18px/28px 字族`），必须**当三元组整体去匹配**，命中就直接用那个语义令牌，**不许拆成三行裸值手写**。
3. **语义层不匹配** → 下沉到基础层，各维度独立就近滑档。
4. **滑档取最接近，不是向上/向下取整**：档位有 18 和 26 时，24 → 26（差 2），20 → 18（差 2）。**等距时向下取**（放大比缩小更容易破坏布局）。
5. **单色滑入基础色板最近的一格**。语义色角色优先：参考的颜色若在其上下文里承担"主色 / 成功 / 危险 / 警告"角色，先映射对应语义 token，再退回色板档位。
6. **渐变不映射，原样保留。**
7. **不需要建议补 token。**

**告知边界**：

- ✅ 语义层命中、↘ 就近滑档 → **静默执行**，只在改动要点里列一行
- ⚠️ **滑档后形态崩坏 → 单独标出问用户**。判据是「形态改变」而非「数值偏移」：4px 高的短杠圆角从 1px 滑到 4px 会变成半圆胶囊、字号滑档导致换行、颜色滑档跨了语义（警告橙滑成危险红）——这类必须问；纯数值偏移（24→26）不问。

**报告格式**（列在改动要点里）：

```
### Token 映射
✅ 语义层命中
   18/28 semibold  → <项目里那个语义令牌>
   #23B283         → <品牌主色令牌>
↘ 就近滑档
   font-size 24px  → <26 那一档> (+2)
📌 保留原值
   linear-gradient(...)  渐变不映射
⚠️ 形态风险
   border-radius 1px → 最小档 4px，会让 12×4 短杠变半圆胶囊 —— 请裁决
```

> ⚠️ **本节不写任何具体 token 名 / 路径 / 档位值**。设计系统会持续迭代、且不是每个项目都用同一套；写死快照必然过期。规则只约定**动作**，具体内容每次去当前项目现查。

### 0.5 🚫 抽公共 class 前，先逐元素核对采集真值——别用"同类应相同"抹平差异（铁律1 高发子场景）

**问题**：一组元素看起来是同类（都是卡片副标、都是列表项、都是标签），写 CSS 时很自然想抽一个公共 class 统一处理。**但"看起来同类"≠"样式相同"**——参考里同类元素常带不同的补充 class，携带有意的逐个差异。一旦抽公共 class 时按"它们应该一样"覆盖，采集件里明明白白的逐元素真值就被抹平了。

**这是铁律1（"拿设计直觉盖了实测值"）的一个具体高发子场景**：不是估错没采到的值，而是**采集件白纸黑字给了差异、却被"规整成一致"的直觉覆盖**——比误差更冤，纯执行疏忽。

**真实翻车**：飞书 6 卡网格，副标 `.fYsEFlf_` 采集件逐张列了 `white-space`：4 张卡有 `nowrap`（单行截断）、内容感知（`.Sg07Q5rF`）和行业模板（`.MPHEclhi`）**无 nowrap**（折行）。写 CSS 时抽了公共 `.desc` 统一处理、没逐张核对 white-space → 折行行为和参考不符，用户圈出返工。采集件数据完全正确、完全够用，是"6 张应该一样"的假设盖了真值。

**硬规则**：

- **抽公共 class 前，把这组元素在采集件「内部结构」段里的属性逐个拉出来比一遍**。完全一致才可合并；只要有一项不同（哪怕只是 `white-space` / `opacity` / 一个 margin），差异项必须单独出规则（`.公共类` 定共性 + `.特例类 .子` 覆盖差异）。
- **警惕信号：参考里同类元素带不同的补充 class**（如 `.fYsEFlf_.ellipsis` vs `.fYsEFlf_.Sg07Q5rF`）——多出来的那个 class 几乎总是在改某个属性，是"这两个不一样"的明确标记，必须去 diff 表里逐项确认它改了什么。
- **合并是优化，不是默认**。拿不准两个元素是否真同，就先分开写，别为了"少几行 CSS"提前合并。

### 2. 🎬 交互行为

**操作**：
- 参考元素有没有 **hover / active / focus / 展开收起 / 滑入滑出** 等动态行为？

- 写代码时必须实现对应的 `:hover` / `.active` 规则

**检查点**：
- ✅ 改动要点里列出了所有动态行为
- ✅ 代码里有对应的交互规则（`:hover` / `transition` / `transform`）
- ❌ 反例：参考卡片 hover 时底部面板从下方滑入，但代码把面板做成了静态显示

**⚠️ 采集件「交互态」段可能漏采，别只看它下结论**（案例 #3 / #6）：
- 参考来自**跨域外站**（非 localhost / 同域）时，hover 规则可能因跨域读 `.cssRules` 失败而漏采（v1.7.0 已加 fetch 兜底，但 `@media` 内的仍漏）。存疑时到 devtools 手动 hover 一次交叉验证。
- 尤其「hover 时**父态驱动子元素**变化」的规则（`.card:hover .child{opacity:0/transform:...}`）最容易漏——它不在 child 自己的 `:hover` 里。看到 overlay / 蒙层默认是 `opacity:0` + **半透明底**时警觉：它靠自身实心底遮住底层，还是靠底层同步隐藏？半透明底 + 没看到底层隐藏规则 = 大概率漏采了联动，不是「淡入半透明层就行」。

**示例**：
```markdown
## 改动要点

- ...
- **Hover 效果**（必须实现）：
  - 图片轻微放大（scale 1.05）
  - 底部面板从下方滑入（默认 translateY(100%)，hover 时 translateY(0)）
  - 面板背景：深色半透明（rgba(0,0,0,0.75)）
```

## 设计输出规范

### 禁用 emoji 作为视觉元素

任何 HTML / CSS / UI 落地，**禁止用 emoji**（🌿/🍃/⭐/✨/🎵 等）作为：

- 图标（badge / category icon / status icon / 标题前图标）
- 装饰元素（角标 / 分隔符 / 引导符号）
- 占位（"先放个 emoji 等下换图"这种偷懒占位）

**Why**：emoji 在不同操作系统 / 浏览器渲染差异巨大（Apple Color Emoji vs Windows Segoe vs Android Noto），无法控制视觉一致性；而且一眼就是"偷懒占位"，跟正经设计的图标系统违和。

**正确做法**：
- 要"图标位" → 走「按图生」重生 / cp 现成资产 / SVG inline 复刻
- 要"装饰元素" → CSS 复刻（伪元素 / SVG / 渐变）
- emoji 不算资产，不算占位，**完全不允许出现在任何 commit 进去的代码里**

### 和「kimi-webbridge」skill 的协作：curl 抓不到图时的默认回退

**默认规则（不问用户，直接执行）**：复刻参考时要 curl 参考里的图片资源，若 curl **实测失败**（403/404 防盗链、`Connection reset` / `SSL_ERROR_SYSCALL` 等 CDN 主动阻断非浏览器请求），**不要停下来问用户"用本地图还是重生"，直接用 `kimi-webbridge` skill 从用户的真实浏览器抓原图**——浏览器带站点会话 + 正确 TLS 指纹，能拿到 curl 拿不到的图。这是采图环节的**首选回退**，优先级高于「按图生重生」和「占位块」。

**为什么是默认**：用户已明确要求「沿用参考原图」时，curl 失败不该降级成"换本地图/重生假图"——那样成品和参考不像；也不该反复打断用户。浏览器抓取能拿到**真原图**，是最忠实的路径，所以设为默认、免确认。

**执行套路**（在页面 JS realm 里 fetch → base64 → 落盘，绕过 curl 的 TLS/防盗链）：
1. `~/.kimi-webbridge/bin/kimi-webbridge status` 确认守护进程 `running:true` + `extension_connected:true`（不健康则读该 skill 的 `references/operations.md`）
2. `navigate` 打开**参考来源站点**（如参考采集页 URL）建立会话上下文，用独立 `session` 名
3. 对每个图片 URL，用 `evaluate` 在页面里跑：
   ```js
   (async()=>{const r=await fetch(URL);if(!r.ok)return 'ERR:'+r.status;
   const b=await r.blob();const buf=await b.arrayBuffer();const bytes=new Uint8Array(buf);
   let bin='';for(let i=0;i<bytes.length;i++)bin+=String.fromCharCode(bytes[i]);return btoa(bin);})()
   ```
   返回的 base64 用 `base64.b64decode` 写进 `./assets/regen/<语义名>.<ext>`（或 `./assets/`）
4. 逐张取（别一次并发太多把响应撑爆）；落盘后 `file -b` 校验是真实图片（`PNG image data` / `JPEG image data`），别拿到错误页 HTML 当图存了
5. 任务末 `close_session` 收尾

**边界**（真到这些才继续降级问用户）：浏览器抓取也失败（该图需要登录态而当前未登录 / 站点强校验 `isTrusted` / 图已 404 下架）→ 这才轮到和用户讨论「按图生重生 or 占位」。**别用假想失败预先跳过浏览器抓取**——先试，实测不行再降级。

> 采图优先级链：**curl（默认）→ curl 失败则 kimi-webbridge 浏览器抓原图（默认回退，免确认）→ 浏览器也拿不到才问用户（重生/占位）**。只有资产是「主题强相关插画/图标/吉祥物且与目标主题不一致」时才**主动**走按图生重生（与 curl 失败无关，是主题不匹配触发的，见下方「资产重生决策」）。

### 资产抠图决策：跟随参考的「实现归属」，不看视觉表象

按图生重生（或 curl 复用）拿到一张资产后，要不要抠成透明 PNG？**判据只有一个——看参考元素的代码实现里，底色由谁承担**，而不是"这张图看起来带不带底板"。

| 参考的实现方式 | 我们照搬 | 抠不抠 |
|---|---|---|
| **底色由代码构成**（CSS `background` / 容器底色），图片本身是透明 PNG 的主体 —— 图和底是**两层** | 目标也用「CSS 底 + 透明 PNG 主体」两层 | **抠**（主体必须透明才能露出 CSS 底） |
| **底色烧进图里**（图片自带底板，是一张完整不透明图）—— 图和底是**一张** | 目标也直接放这张完整图 | **不抠** |

**判断动作**（必须在**填生图 prompt 之前**做完——因为它反过来决定 prompt 的背景字段）：

**第 1 步是强制客观核对，不许跳过、不许凭印象——判据由命令输出产生，不由"看着像"产生：**

1. **【强制】curl 参考源图到 /tmp，跑一行命令查 alpha 通道，把实际输出贴出来**——这一步的输出是抠不抠的**唯一权威依据**：
   ```bash
   ~/.claude/skills/按图生/.venv/bin/python3 -c \
   "from PIL import Image; im=Image.open('/tmp/ref-xxx.webp'); \
   print('mode:',im.mode); \
   print('alpha:', im.getchannel('A').getextrema() if 'A' in im.mode else '无 alpha 通道')"
   ```
   - 输出 `alpha: (0, 255)`（或下限 < 250）→ **源图有真实透明区 = 主体浮在透明底上 = 抠**
   - 输出 `无 alpha 通道` / `alpha: (255, 255)` → **源图是完整不透明图 = 不抠**
   - **写不出这行命令的实际输出 = 判定无效**，回去补跑。**禁止**用"我看图像是白底/带底板"代替这一步。
2. 交叉验证采集数据：参考那块底色是 CSS `background`（图/底两层）还是烧在源图里（一张）？应与第 1 步结论一致；不一致就停下来查清，别硬判。
3. 分流：
   - **有 alpha（CSS 底 + 透明 PNG）** → **抠**：生图 prompt 写 `背景:纯白`（给 cutout 干净底）→ 出图后 `cutout.py` 抠成透明 PNG → 叠到目标 CSS 底上（目标卡背景也照参考用 CSS 三层，别做成"cover 铺满一张白底图"）
   - **无 alpha（图自带底板）** → **不抠**：生图 prompt 写 `背景:纯色/纯白`（照参考底色）→ 完整图直接用

**⚠️ 表象陷阱——下面这些都是伪信号，一个都不能拿来判抠不抠**（判据只认第 1 步的 alpha 命令输出）：
- ❌ "图在目标卡里是 `object-fit:cover` 铺满的" —— cover 只是**目标侧的显示方式**，跟**参考源图透不透明**毫无关系。透明 PNG 照样能 cover 铺。（2026-07-19 就是栽在这，把"cover 铺满"当成"完整图→不抠"）
- ❌ "curl 下来用 Read 看，渲染出来像白底" —— 透明 webp/png 被 Read 渲染时透明区常被填成白，**看着像白底 ≠ 没 alpha**。必须查通道，不能靠肉眼看渲染图。
- ❌ "它看起来带/不带底板" —— 视觉表象一律不算数，只认命令。

**两条硬纪律**：
- **豆包出不了真透明底**——它只出纯色/白底的不透明图，透明只能靠后处理 `cutout.py` 得到。prompt 里**不要**写 `背景:纯透明`（对豆包无意义还误导），要透明就写 `背景:纯白` + 事后 cutout。
- **抠不抠在填 prompt 前锁定，别到交付才改口**——这个决策还影响 prompt 的背景字段和是否要压主导色 DNA（若底板是参考主导色载体、又决定不抠，底板色就得保住）。线框图要点里的抠图声明必须和 prompt 背景字段一致，不许自相矛盾。

**两个方向相反的反例（凑齐才完整——一个"该抠误判成不抠"、一个"该不抠误判成抠"倾向）**：
- **反例 A（2026-07-19，该抠→误判不抠）**：复刻创客贴功能卡的右侧配图，参考源 webp 实为 `RGBA`、alpha `(0,255)`（透明主体 + CSS 三层背景），**本该抠**。但只凭"图在目标卡里 cover 铺满右侧"就判了"完整图→不抠"，跳过了 alpha 核对；curl 下来 Read 看又是白底渲染、更坐实了误判。用户看 devtools 的透明棋盘格缩略图才发现。**根因：把 cover（目标显示方式）+ 白底渲染（Read 假象）当判据，没跑 alpha 命令。**
- **反例 B（2026-07-19，决策反复）**：复刻百度千帆应用卡图标，线框图要点写了"交付后跑 cutout 抠透明"，到交付才改判"不抠"。根因同样是没在填 prompt 前跑 alpha 核对（该图源 PNG 无 alpha、自带底板 → 本该一开始就定不抠）。

### 去水印：交付后的独立收尾关（判据是「实际看图」，不跟抠图绑死）

豆包产物右下角**必带**"豆包AI生成"水印。处理它有一条**独立**的收尾关，和抠图**正交**——不能用"抠了就默认没水印"替代：

- **判据是「处理完成后，Read 一眼成品右下角还有没有水印」**，不是"抠没抠图"。抠图**可能**顺带把水印（落在被丢弃的背景区）去掉，但**不保证**——水印压在主体上、或贴主体边缘时会被算进主体一起留下，抠图模型对半透明水印判断也不稳。
- 所以**无论抠没抠图**，交付前都要看一眼成品右下角：
  - 还有水印 → 走「去水印」skill（或 `remove-watermark.py`）去掉
  - 已经没有（抠图顺带去掉了 / 本就无）→ 跳过
- **去水印是独立 skill、独立能力**——它服务任意来源的图（不止按图生产物），保持独立入口；复刻主流程只是在这道收尾关按需调它一下，**不把它吞进按图生主流程**（同 cutout 定位：工具独立、决策和执行权在调用方）。

**反例（2026-07-19）**：这次交付的带底板图标（决策=不抠）右下角残留豆包水印，按图生交付时没有任何提示，靠临时写脚本救火。根因是当时既没把"去水印"当成一道必过的收尾关，也一度误以为"抠图能顺带解决水印"——两者其实正交。
